核心命题

113|

同等能力的模型越来越多，但产品间的体验差距反而在拉大。原因不在模型，在「怎么用模型」——这个「怎么用」就是 Harness Engineering（驾驭工程）。

114|
模型不是瓶颈，harness 才是。
115|

一个惊人的实验：同一模型只改 harness 不改模型 → Terminal Bench 2.0 得分从 52.8 飙到 66.5，排名从 30 开外冲进前五。另一个实验：同一模型同一提示词只改运行环境 → 成功率从 42% 提升至 78%，效果堪比换一代模型。

AI 编程的三次范式跃迁

120| 121| 122| 123| 124| 125|
阶段时间核心局限
Prompt Engineering2022–2024写好一条指令（Few-shot, CoT, 角色设定）一次性输出，无迭代
Context Engineering2025动态构建上下文环境上下文窗口仍是瓶颈
Harness Engineering2026 →约束体制 + 反馈回路 + 工作流控制仍在快速演进
126|

每一轮跃迁的本质是：把更多「怎么做」从人脑移到了系统里。提示词时代靠人写好每一句；上下文工程时代靠框架动态组装信息；Harness 时代靠约束和回路让 Agent 自主工作。

Harness 四大核心组件

131| 132|
133|

1. 上下文工程（Context Engineering）

134|

AGENTS.md 控制在 60 行以内，过长反而降低表现。每次犯错把规避规则更新进去。好的上下文是吃出来的，不是写出来的——AI 做错了就记下来，下次就不会再犯。

135|
136| 137|
138|

2. 架构约束（Architecture Constraints）

139|

用 Linter 和结构测试机械执行，不是靠 prompt 说「请遵守」。违反直接 CI 挂掉，报错信息嵌入修复指引。「约束比指令更有效」——Cursor 团队的核心发现。

140|
141| 142|
143|

3. 反馈循环（Feedback Loop）

144|

Build → Verify → Fix 闭环。Agent 对 Agent 审查——「写 bug 的人修 bug、提 bug 的人验收」。Pre-completion Checklist 拦截在退出前，不让半成品出门。

145|
146| 147|
148|

4. 熵管理（Entropy Management）

149|

AI 代码会积累过时文档、架构漂移、风格走样。定期启动专门 Agent 做垃圾回收（Dogfooding Agent）。好的 Harness 不止管怎么建，还管怎么维护。

Agent 三种失败模式

155|

Anthropic 内部总结出 Agent 最常见的三种失败模式：

156|
    157|
  1. 试图一步到位（One-Shooting） — 一个会话写完所有功能 → 上下文耗尽 → 留下半成品。几乎所有翻车都从这里开始。
    2. 158|
  2. 过早宣布胜利（半场开香槟） — 完成部分核心功能就判定任务完成，隐藏的 bug 直到验收才暴露。
    3. 159|
  3. 过早标记功能完成 — 看起来能跑，实则隐藏边界 bug，测试覆盖率明明不够却说够了。
    4. 160|
161|

这三种失败模式指向同一个解决方案：别让一个 Agent 做所有事，用多 Agent 分工协作。

多智能体协同实战架构

166| 167|

方案一：Ralph 循环

168|

核心是一个 while 循环，不断用 claude CLI 启动新会话。每轮 AI 读取同一段提示词 → 了解进度 → 挑一个未完成的任务 → 执行 → 标记完成。前后 AI 通过文件系统交流。

169|

局限：「自己开发自己测试效果一般」，缺少独立质量回检环节。

170| 171|

方案二：多智能体协同（推荐）

172|

Claude Code 主会话作为主 Agent（项目经理），不写代码，只协调子 Agent：

173| 
需求文档 → 主 Agent
   174|  ↓
   175|计划子 Agent → 制定计划文档 → 返回路径
   176|  ↓
   177|主 Agent 取出任务 → 开发子 Agent 执行 → 返回文件路径
   178|  ↓
   179|主 Agent → 3 个测试子 Agent 并行（布局/美观/动画）
   180|  ↓ 测试失败
   181|主 Agent → 让原开发子 Agent 修 bug（保留上下文）
   182|  ↓ 修完
   183|主 Agent → 让原测试子 Agent 验收
   184|  ↓ 通过
   185|继续下一个任务 → 全部完成

关键原则

189|

「写 bug 的人修 bug、提 bug 的人验收」

190|

修复时传入子 Agent ID，让同一个人接着修；验收也让同一个测试来验。修正循环最多 3 次，防死循环。开发用低成本模型，测试用高质量模型——资源分配给最需要的地方。

191|
192| 193|
194|

经验沉淀机制

195|

开发修完 bug 后把经验写入文件 → 前面踩的坑马上成为后来者的经验 → 事后完善 skill。「不要让 AI 犯相同的错误」——每次迭代积累的知识库让系统越做越好。

四大实操技巧（LangChain 实践）

201|
    202|
  1. Trace 分析 — 执行日志做成 skill，失败后自动分析、自动改 harness（类似 ML 的 boosting 思想）
    2. 203|
  2. Local Context Middleware — 自动注入目录结构、工具路径，避免 AI 在陌生环境迷路
    3. 204|
  3. Doom Loop 检测 — 同一文件反复编辑超阈值时提示「请重新审视方案」，避免在原地打转
    4. 205|
  4. 工具越少越好 — Vercel 实验：15 个工具砍到 2 个，准确率 80% → 100%
    5. 206|

终极形态：「结果 + 预算」

225|

Anthropic 认为平台的最终形态可能压缩为两个参数：Outcome（想要达到的目标）和 Budget（愿意花多少 Token）。剩下的全部由 Claude 自行决策——用哪个模型、启动哪些子 Agent、按什么顺序执行。

这指向 Agent 时代的终极抽象：从「提供 API」进化到「理解你的目标并自行执行」。

Skills 作为可组合单元

231|

Anthropic 通过 skills 来管理 Agent 能力生命周期。新模型发布后如何升级正在运行的旧 Agent？更新 skill 即更新 Agent。Skills 是 Hermes 自带的特性，也是 Claude Code 持久化上下文的关键机制。

Big Model vs Big Harness 之争

237| 238| 239| 240| 241|
阵营代表人物观点
Big ModelOpenAI Noam BrownHarness 是拐杖，终将被超越
Big HarnessLlamaIndex Jerry Liu模型是引擎，harness 是方向盘和刹车
242|

结论：两边都对一半。模型越强 harness 应该越薄，但变薄不等于消失。时速 30km 可以没护栏，时速 120km 必须有，时速 300km 的高铁全程封闭轨道本身就是 harness。

终极结论

247|
只会写代码的程序员一定会被取代，但会设计 harness、会驾驭 AI 的工程师会迎来自己的黄金时代。
248|

工程师价值从写代码 → 设计让 Agent 可靠工作的系统。OpenAI 团队不写代码，写规则；Stripe 不写代码，写 Blueprint（确定性节点 + Agentic 节点混合编排）。
