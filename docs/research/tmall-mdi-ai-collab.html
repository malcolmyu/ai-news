天猫 MDI：AI 研发协同从「超级个体」到「全员赋能」的四级进化

淘天集团天猫技术团队在「天猫新品 MDI」项目上的 collar SDD 体系实践：用 AGENTS.md 入口地图 + 六模块知识库打造「超级个体」，用站点地图与上下文缝补横向复刻出团队，再用一台零依赖「技术哨兵机」还原预发合并态（冲突发现率 >70%），最终以 NekoCollar 云端协作平台把研发能力辐射到非研发角色。

01 · 核心命题

效率要从「个人偶得」变成「团队可复制」

作者开篇给出一个判断：AI 作为生产力工具，带来的不是一次从顶层发生的效率革命，而是一条从一线生长、向组织逐级放大的生产力曲线。只有把效率从「个人偶得」变成「团队可复制」，AI Native 的成熟实践才有可能跨团队、跨业务复制，形成组织乃至集团层面的规模效应。
"AI 作为生产力工具，带来的不是一次从顶层发生的效率革命，而是一条从一线生长、向组织逐级放大的生产力曲线。"— 天猫技术团队 · 卡狸
02 · 项目背景

一个横跨 4 角色端、约 40 模块的全栈平台

天猫新品 MDI 是一个全新的业务项目：不是单点功能，而是横跨 4 个角色端、约 40 个功能模块的全栈平台，再叠加外部智能投放系统、算法内核与自动化评测体系、阿里云百炼全模态等外部依赖。
多位同学并行采用 SDD（规格驱动）高频敏捷开发，严格每周线上迭代一个大版本。最夸张的一次上线时，同时存在 8 个仓库、十几个分支在预发集成开发。它几乎完整命中了「AI 时代项目」的所有显著特点。
03 · 能力放大主线

个体 → 团队 → 可持续 → 全员

四个阶段串起来，要解决的是一条朴素的「能力放大」问题：先让一个开发者成为「超级个体」，再让超级个体组成「超级研发团队」，再让这支团队可持续地跑下去，最后把研发能力辐射到项目组的每个非研发人员。
阶段 要解决的问题 核心手段
单兵攻坚期 AI 不知道这个项目是什么 结构化知识库 + collar 三层约束

高速迭代期 效率上来了，质量开始劣化 技术哨兵机还原预发合并态 + 云端 Agent 冲突检测

04 · 单兵攻坚期

构建极具纵深的「超级个体」编码上下文

单兵作战时最大的痛点不是「不会写代码」，而是AI 不知道这个项目是什么——不知道业务地图、踩过的坑、为什么选了这个技术方案。每开一个新会话，上下文都要重新灌一遍。解题思路是用一个结构化知识库把整个全栈项目集成在一起，这就是他们称之为 collar（项圈）的 SDD 研发体系——给自由奔放的 AI Agent 套上一个边界与知识的项圈。

命名渊源：neko（猫）与 collar（项圈）

团队有一系列以 neko（日语「猫」）命名的产品——neko、nekoClaw、NekoCollar，而 collar 正是给「猫」戴的项圈/牵引具（harness）。这跟开篇提到的「AI 上下文是效率关键」一脉相承：约束不是束缚，而是让 Agent 在边界内高效驰骋的牵引绳。

手段一：AGENTS.md —— 每个会话必加载的入口地图

根目录一份 AGENTS.md，是 Agent 进入项目的唯一入口，铁律写在开头：「本文件是 Agent 的入口地图（≤120 行）。不放细节，只告诉你去哪里找。」它用几个精炼板块串起一个多仓库聚合工作区（前端主应用 + 5 个微应用/H5 + Java DDD 四层后端 + Node 评测执行端 + 评测服务端）：
  • 仓库地图：带注释的目录树，一眼看清 7 个子仓库各自是什么、端口多少、哪个是唯一开发入口、哪个已废弃禁止改动
  • 快速命令：每个应用怎么启动、怎么 build/lint，AI 不用翻各仓 README
  • 关键约定速查表：把「踩过坑才总结出的强约定」浓缩成「一句话 + 详见链接」
  • 当前状态表：每个应用「完成度 + 已具备能力」的实时快照
AGENTS.md 的行数由 collar-runbook skill 主动「守卫」——一旦逼近 115 行就提醒把详情迁到 docs/，入口地图永远精简可信。

手段二：六个 Skill 管理知识库的六个层级

知识库拆成 docs/ 下的六个模块，每个模块配一个唯一对应的 Skill（统一 collar- 前缀），构成「模块 ↔ Skill ↔ README」三位一体：
docs/
├── specs/        业务地图（要做什么）        → collar-specs
├── changelog/    做了什么 + 将做什么（时间线） → collar-changelog
├── architecture/ 系统怎么连的（8 类连接点）    → collar-architecture
├── runbook/      零散过程知识（8 类）          → collar-runbook
├── vendor/       外部源码选择性同步           → collar-vendor
└── wiki/         自由知识库（人工维护，中文）   → collar-wiki
最关键的是一条底层信念：「对 Agent 来说，看不到的知识等于不存在。」所以所有知识必须版本化落到仓库文件里，一旦发生就自动沉淀进 docs/，下一个会话或下一个人拉取仓库就能获得完整上下文。
单个 Skill 好做，难的是让多个 Skill 不打架还能配合。办法是把 git commit 设计成统一的触发关卡——一次提交，三个 Skill 从三个正交维度同时喂养知识库：changelog 记「做了什么」，runbook 抽「学到了什么」，specs 检「代码是否偏离了意图」。这里的「强制」是真强制——知识沉淀从「靠自觉」变成「流程门禁」，杜绝「这次先算了、下次一定」的滑坡。

手段三：人工与自动双方式实现知识库冷启

知识分两类各归其位：人工维护（设计理念、竞品分析、blue-print 蓝图调研）进 wiki/；自动维护（changelog / architecture / runbook 三层）由 AI 从 git、代码、对话中自动提取沉淀。官方 demo 代码走 vendor/ 模块，核心原则是「只做减法、只下载我们所需要的」。vendor 不只是「存代码」，它还是 collar-specs 的实证参考源——specs 生成技术方案时会自动扫描相关 vendor，提取代码模板、API 用法、架构模式，融入方案并标注来源。一句话点睛：「用户放进 vendor 的代码不一定完整阅读过，这一步帮用户『读』并提炼要点。」

手段四：给 AI 套一个「项圈」——三层心智模型

根目录还有一份 collar.yaml（在 NekoCollar 上渐进落地中），把「项圈」抽象成三层值得记住的心智模型：
Identity（身份/知识入口）：告诉 AI「你是谁、去哪读知识」
Boundary（边界/约束）：明确 AI「能碰什么、不能碰什么」，核心逻辑是默认拒绝（deny-by-default）
Validation（验证）：改完代码必须过的门禁（lint / typecheck）
一句话：Identity 管知道什么、Boundary 管能改什么、Validation 管改得对不对。即便 collar.yaml 还在完善，这套三层模型已通过 AGENTS.md、pre-commit hook、以及后文 NekoCollar 的软硬双锁在各处启用了。
05 · 加人提速期

基于能力分发，横向复刻出「超级研发小分队」

单人攻坚一个月后加人，核心问题变成：如何把单人的效率复刻到多人协同。多人协同最怕两件事——一是冲突（大家改到同一处），二是上下文断裂（为了工程规范把逻辑外置，结果 AI 看不懂了）。

手段一：借鉴 Web2.0 的站点地图，物理隔离分工

站点地图（sitemap）的价值在于：动工之前就把整个系统的疆域横向铺开、切分清楚。docs/specs/ 就是 MDI 的站点地图，按业务地图铺开：管理端 16 个功能模块、用户端 6 个、小二端 14 个、专家端 1 个、评测端 2 个。一个业务地图 = 站点的一个分区，一个功能模块 = 分区里的一个页面/功能区，数字前缀保证目录天然有序。
「目录即认领单元」——A 认领「创建项目」、B 认领「项目循环」，各自的 spec 目录物理隔离，冲突面降到最低。进入开发前就确认清楚每个人负责的产品前台路由、后台 API 领域、产品模块和 spec 范围。

手段二：四种变更类型满足所有需求演进行为

一个 feature 的三级结构：raw提示词.md（原始需求，只追加）→ 主 spec [技术方案]xxx.md → patches/（挂载的 PATCH 集）。四种类型覆盖完整生命周期：
  • blueprint：放在 docs/wiki/blue-print/（自由探索层），是「还没确认如何沉淀成 spec 的基础能力构思」，命名前缀体现成熟度阶梯 [调研]→[讨论稿]→[技术方案]…V4-MVP，成熟后才「毕业」迁入 specs
  • feature：稳定功能，活在 docs/specs/（正式规格层）
  • patch：小改动走 PATCH 补丁，多人可在同一 feature 下并行提交，主 spec 只在稳定后收敛
  • sunset：旧功能优雅退场

关键规格一：patch 的双向指针解决「主文档与补丁」的语义二义性

当一个 patch 要替代主方案里的某段内容时，如果只在 patch 里说「我改了 X」，读主文档的人不知道；如果只在主文档划掉「X」，读 patch 的人不知道来龙去脉。所以强制双向建立指针：Patch 开头用「覆盖范围」表声明替代了主方案的哪段；主文档被替代段落加删除线 + superseded 指针指向 patch。核心要求是 Patch 自身必须可独立阅读，不依赖读者先读主文档——这对 AI 尤其友好，从任何文件切入都能拼出当前生效的真相，不被过期描述误导。

关键规格二：sunset 让旧功能优雅日落

旧功能下线如果直接 git rm，那段历史上下文就永久丢失了，未来排查灰度期线上问题会抓瞎。sunset（日落）让旧 spec 优雅退场——真实案例是用户核心循环从 V1 自建 LLM Agent 迁移到算法团队的 TPP 服务：V1 文档进入「凝固期」，不修订、不新增 PATCH、仍可阅读用于排查，直到 V2 全量切换且稳定 1 周后整体 git rm。sunset 不是「把文件删掉」，而是一份带状态机的可执行迁移剧本。

手段三：提交时，代码到 spec 的反向提醒

站点地图把疆域切好了，但代码写着写着可能偏离 spec。设计哲学非常关键：
"Spec 是意图源，比代码更早期。代码偏离 Spec 不一定是错误——可能是编码过程中发现了更好的方案。"— 天猫技术团队
所以提交时不自动反向更新 Spec，而是输出差异清单，把决策权交给人：每个差异点列「Spec 描述 vs 代码实现 + 建议」，用户逐条决策——反向更新 Spec / 保持 Spec 不变（记 TODO）/ 暂时搁置。这把「文档变化」从静默忽略变成了显式决策，配合 lint 质量门禁 + collar-changelog 强制约束，构成「Agent 语义检查 + git hook 质量检查」的双保险。
06 · 上下文缝补

工程优化不能捅破 AI 上下文——这是全文最有价值的部分

多人协作到一定阶段，一定会为了发布效率把某些硬编码（比如 prompt 逻辑）迁移到 Diamond、DB 或其它持久化介质上。这在传统研发时代是标准「最佳实践」（配置与代码分离），但在 AI 研发时代是一个隐蔽的陷阱：Agent 的行为逻辑写在代码里时，codeAgent 一读代码就知道它会怎么干；一旦提示词挪到 DB，代码里只剩一个 promptService.load(agentCode) 调用框架，codeAgent 再读代码就完全不知道这个 Agent 的具体行为——它会在关键决策上误判，或给出那句让人血压升高的话：「但我不知道这个 Agent 的具体行为，请你去对应平台修改相关的提示词。」这就是推理链断裂：你以为做了工程优化，实际上把 AI 的上下文捅了个窟窿，研发效率断崖式下跌。

一条原则 + 一个更根本的认知

项目组立下的原则：任何导致上下文异常的研发架构变动，都必须用适合的方式缝补缺损的上下文。背后的认知是——AI 时代 human in the loop 越少效率越高，所以 AI 上下文始终是效率的关键（注意：这里说的是效率，不是质量）。DB 相关的 MCP 为什么好用？就是让业务逻辑链路重新完整、让 codeAgent 上下文齐全。
案例 上下文缺损点 缝补方式
外置动态提示词/skill Prompt 工作台动态管理、独立发布，代码只有调用框架 MDI 专属 MCP Server 暴露 20 个只读查询工具 + 一个使用说明书 skill
预发/线上环境差异 「隐藏地形」，排查预发问题出现无法解释的现象 在 AGENTS.md「关键约定速查」显式声明，细节沉淀成 ADR
Transform 脚本（Groovy） 运营逻辑外置到平台，AI 读脚本不知脚本是什么 //! 声明式注释保留上下文锚点——Groovy 眼里是普通注释，对平台却是元数据
其中案例一是完整闭环的典型：光有 MCP 还不够——工具「能查」不等于 AI「知道该查」。所以额外配了一个 skill 作为 MCP 的使用说明书，明确回答三个问题：何时查（定义触发条件，主动调 MCP 而非等人提醒）、怎么查（固定四步调用链，锚点 = 场景码 + Agent 码）、查到后怎么用（补充 MCP 数据含义）。MCP 提供「只读可达」的通道（能力层），skill 提供「何时/如何取用」的协议（认知层）——两者合起来，codeAgent 才会主动按正确锚点把外置到 DB 的上下文拉回视野。
07 · 高速迭代期

引入「技术哨兵机」，从更高维维稳

进入第三阶段，节奏变成每周一个大版本、预发同时十几个分支。新问题浮现：效率提升后，人与人之间对新输入的上下文交换效率成了瓶颈——上午改了后端接口签名，下午改了前端调用，各自本地都跑得通，合到预发业务逻辑一冲突，甚至要延续很久之后才炸。这种「隐形冲突」在多人高速迭代下指数级增长，是 AI 研发质量劣化的头号杀手。

手段一（失败的尝试）：Agent Manage 编码态监控

最初的想法很直觉：直接读取大家本地编码阶段的输入和 Agent 输出（监听 cursor、qoder、claude code 等进程），在编码阶段就把冲突扼杀。结果遇到两个致命问题：噪音太多、信噪比极低（没 release 前的本地编码态充满了写了又删、试了又改的无用噪音），成本过高（监控每个人本地编码态 token 消耗惊人）。失败的根因事后复盘很清楚：介入时机放错了——编码态是「意图尚未定型」的阶段，信息熵最高、确定性最低。

手段二（这次有戏）：把触发节点后移到「预发集成态」

复盘后把触发节点从「编码态」后移到「预发集成态」，collar-daemon 登场：一个跑在独立机器（目标形态 Mac mini）上长驻的守护进程，本质是「团队研发质量的哨兵」。技术栈极简——原生 Node.js、零第三方依赖，只用 child_process/https/net/fs 内置模块。它做三件事构成闭环：
  1. 代码环境还原：持续把「线上」和「预发」两套工作区的所有子仓库同步到各环境的最终态（预发每 300s 轮询，自动发现最新 release 分支，前端走 def_releases_*、后端走 releases/*）
  2. 业务逻辑冲突检测：预发一拉到新提交，就把「谁改了什么」喂给云端 AI Agent 做隐形冲突分析
  3. 告警闭环：Agent 发现冲突，通过钉钉机器人 + AI 表格告警到群里

为什么「始终维护一份 release 集成分支」如此关键

每个开发者本地只有自己那一部分的改动，分支各不相同——除了集成环境本身，没有任何一台开发机拥有「所有人最新提交合在一起」的完整环境，而恰恰是这个「合在一起」的环境才是冲突真正暴露的地方。哨兵机在工作区层面模拟出了「预发合并态」：一个可运行、可被 AI 通读的完整快照。典型冲突只有在集成态才现形——A 改了接口签名 B 恰好在调用、甲改了共享 Prompt 的槽位 key 乙依赖旧 key、DB 字段变更、并发时序、共享配置……这些在任何单一开发分支上都「一定不存在」。
几个细节：daemon 代码不做任何规则判断、不内联任何 prompt，只把结构化上下文 POST 给云端的 QoderWake Automation Agent 判定冲突——易变的智能（prompt 编排）放云端，本地进程零依赖、长期稳定。信息采集时精确提取每个新提交的作者、message、变更文件，按仓库分组、每条突出提交人名字——因为多人协同排查冲突时，「谁改的」是第一线索。还有个工程小巧思：QoderWake 管理界面硬编码绑定 127.0.0.1，daemon 用 net.Server + pipe() 做了同端口不同 IP 的 TCP 透明转发，让全团队远程看哨兵机界面。

北极星指标：周冲突有效发现率 >70%

如果冲突检测只停留在「群里发条告警」价值会大打折扣——告警会被刷走、没人跟进、无法度量。所以把 Agent 每轮产出的冲突沉淀成一张钉钉 AI 表格，做状态流转管理（待回复 → 问题存在/误报/已修复），既闭环问题、又反向校准 Agent 准确率。北极星指标是「周冲突有效发现率」。真实成效：业务冲突有效发现率稳定超过 70%（Agent 报出的冲突七成以上是真问题），每周发现 40+ 个单人视角根本看不见的隐形业务埋雷。更有意思的是团队心态变化——如果哪天哨兵机没有发冲突检测，大家普遍心理不安，担心哪里悄悄埋了雷。团队会对一个 AI 工具产生「没有它就不踏实」的依赖，说明它真正嵌进了研发流程。
08 · 稳定运作期

NekoCollar：把效率和稳定性平权给非研发角色

研发的效率和质量上来了，那测试、产品、设计这些非研发同学呢？他们同样需要理解代码、基于当前系统提出改动、需要「所见即所得」的编辑体验。作者指出一个深层原因：代码是距离用户真实体验最近的一份「可执行事实」——产品文档、设计稿、测试用例都是最终系统的不同投影，用户最终体验的是代码与配置实际运行出来的行为。围绕代码协作，不是让所有人进 Git，而是让所有角色都基于最终可执行事实工作。
但直接把 git 权限、AI 编码能力交给非研发角色风险极高。本章与前三章最本质的区别在于：前三章的参与者都懂代码、懂 git、有工程素养，约束可以相对「软」；当参与者扩展到测试、产品、设计，约束就必须从「软」变「硬」——「参与者的工程素养越低，系统的约束就必须越硬。」NekoCollar 的设计哲学一句话概括：在效率上做加法，在稳定性上做物理约束。

效率线：云端沙箱 + 所见即所得的真实页面编辑

非研发同学不需要本地配环境：系统用一套异步编排（WorkspaceProvisionOrchestrator，@Async 五步流水线）在云端 Aone 沙箱一键拉起工作环境。关键在 Step3——先 clone 知识库作外层目录，再把代码仓 clone 进知识库内部，这就是研发态实际用到的真实「上下文」环境。
最不一样的一点是「所见即所得」：市面上多数「AI 改前端」产品要么在隔离沙盒预览页看效果、要么给一段 diff 让你想象，都不是「真实页面」。NekoCollar 的完整链路是：沙箱内跑真实 dev server（npm run start）→ 端口通过 Aone Sandbox SDK 映射成外部 URL 注册 → 浏览器插件（nekocollar-extension）打开预发/线上真实页面时，自动把该页从 CDN（g.alicdn.com）加载的前端资源实时重定向到沙箱 dev server 的 endpoint。于是产品/设计同学在沙箱里跟 codeAgent 对话改页面，真实页面上即时看到 AI 编辑的结果——不是仿真、不是预览、不是 diff，就是那个真实页面本身实时变化。原本只有研发用 whistle/charles 代理才能做的「调试真实页面」，现在无门槛交给非研发同学。服务端改动（接口返回结构变化）目前规划用浏览器插件 mock 方式就地拦截（前端静态资源代理已扎实落地，接口 mock 属规划中）。

稳定性线：软硬双锁把危险操作变成「物理不可能」

硬约束（协议层，不可绕过）：沙箱 clone 完代码后，第一件事就是遍历所有 git 仓库，把 push URL 改写成一个不存在的仓库名（PUSH_DISABLED）——此后任何 git push 都会报 fatal，沙箱里的代码只能进、不能推出去污染主干。
软约束（行为层，减少无谓尝试）：写入沙箱 ~/.claude/settings.json，permissions.allow 白名单只放行拉取类 git 命令（fetch/pull/merge/rebase/checkout/add/status/log/diff），push/remote 不在白名单，ACCEPT_EDITS 模式下审批直接失败被拦截。
两道锁都已真实落地，在此基础上还规划了第三道锁——提案审阅兜底（开发中）：非研发同学在沙箱里改得满意后，这些改动不直接落库，而是先沉淀为一份结构化提案（已验收净 diff + 需求 + 决策 + 验收证据），经审阅后才被智能 cherry pick 应用。三道锁合起来，非研发角色才可能安全地基于代码库表达意图。
09 · 结语

AI 时代研发协同发展的四条必经之路

回望四个阶段，四条可直接复用的经验，每条都对应一个「解法 + 原因」：
阶段 解法 原因
单人起步 构建核心全栈上下文 知识库深度直接决定原子单位研发效率
多人扩张 构建 spec 变更规则和站点地图 权责划分清晰度决定效率能否横向扩散
敏捷迭代 构建比传统研发更高维的 AI 监控机制 传统维度手段无法让质量与效率同步提升
项目稳定 构建更多易用的协同链路 + harness 工程 新链路设计决定能否把效率和质量辐射至非研发人员
"把 AI 带来的研发能力一层层往外放大：个体 → 团队 → 可持续 → 全员。"— 天猫技术团队
先让一个开发者成为超级个体，再让超级个体组成能协同的超级团队，再让这支团队可持续地高速跑下去，最后把这份能力辐射到非研发的每一个人。作者最后一句收束：AI 能力普惠后，人心中那些不固步自封、追求和创新的特质才是最宝贵的。
