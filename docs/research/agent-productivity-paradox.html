Agent 时代的生产力悖论：当协作本身成为最大的瓶颈

约束不再是代码生产的速度，而是软件组织的结构。阿里巴巴 Aone 团队揭秘内部面向 Agent 的研发模式升级实践。
Aone 阿里云 Agent-native 研发范式 协作瓶颈 Multi-Agent
核心隐喻

「光换引擎不改底盘，就像在牛车上绑火箭」

19 世纪末工厂将蒸汽动力换成电力，头三十年生产力几乎毫无起色。直到 1920 年代企业从车间动线到岗位协同彻底重塑，流水线诞生，效率才质变。
"今天同样的剧本正在AI领域上演。企业给每个人都装备了AI工具，底层的组织形态、协作机制、管理逻辑却纹丝未动。每个人都换上了最好的桨，但没有鼓手统一节奏、没有舵手校准航向——桨划得越猛，船反而越乱。"
— 向邦宇，阿里代码平台负责人
问题 ①

传统分工是 Agent 的「死锁」

AI 生成代码质量已不再是问题。痛点前三：
🧩 上下文碎片化
Agent 要在多团队、多工具、多仓库、多文档系统间来回切换，每次切换丢失重建上下文
🔗 接口摩擦
前后端 API 契约定义、联调、变更管理——AI 完全有能力自动生成一致代码，却被迫人工走流程
🏝️ 知识孤岛
每个领域知识被隔离在特定团队或文档中，AI 无法获取全局视角做最优决策
问题 ②

研发阶段的信息断层

需求分析（PM）与代码实现（开发）的分离，基于一个已经过时的假设：需求必须被人理解和翻译后才能进入实现。
自然语言即代码 — AI 可直接理解自然语言需求并生成实现，不再需要人工翻译
需求即测试 — 好的需求描述包含验收标准，可直接转化为自动化测试用例
当 AI 可以直接从 Spec 生成代码时，传统分工就是效率的阻碍。
问题 ③

代码是分离的，文档是分离的

Agent 面对的第一个挑战不是「如何写代码」，而是「代码在哪里」：
• 客户端一个仓库，前端一个，后端 N 个微服务仓库，SDK 又独立版本管理
• 需求在语雀，API 在 Swagger，讨论在钉钉，Bug 在 Issue 系统，代码注释散落在各处
• 这些信息实体之间 没有关联、没有索引、没有机器可读的元数据
"对人类来说，可以搜索、问同事、凭经验定位来拼凑上下文；但对 Agent 来说，这些信息孤岛是无法逾越的鸿沟。"
问题 ④

人维护文档 vs Agent 生成文档

传统文档的致命问题：
📉 文档更新永远滞后于代码变更
😰 最了解系统的人最忙，没时间更新文档
🤷 有时间更新的人对系统了解不够深入
解药：把文档视为「代码」——由 Agent 生成、修改、验证，与代码一起版本控制、一起审查、一起自动化测试。
问题 ⑤

Agent 在交付和稳定性链路中的缺席

Agent 会写代码、会跑测试，但——
❌ 无法直接触发构建
❌ 无法自动部署到预发
❌ 无法推进到生产
❌ 无法参与灰度决策
❌ 无法自动回滚
原因：
• 权限分散在不同系统和角色手中
• CI 日志、测试报告、性能指标散落不同系统，无统一接口
• 灰度调整、回滚判断通过站会和即时沟通完成，Agent 无法参与
"任何将 Agent 排除在外的环节，都是 AI 时代研发效率的瓶颈。"
解决方案

让 Agent 更好工作的 5 个关键要素

📦
All In Code 信息管理
代码、文档、测试、配置、记忆全部纳入统一 Git 仓库。AI 在完整上下文中工作，无需跨系统切换。
🔒
隔绝外部依赖·版本化一切
外部文档定期抓取版本化存储、需求库版本化、依赖精确锁定、Mock 服务隔离。构建自包含可复现的研发世界。
🔄
自学习与自我迭代
每次产出经过验证 → 结果记录 → 优化后续行为。AI 学习团队编码风格，生成的代码越来越符合团队偏好。
🛡️
Agent 安全执行能力
沙箱隔离、权限分级、分批执行、审计日志、Dry Run 模式、仿真环境（DB/ES/MQ/Redis 模拟）。
✅
研发后验证能力建设
E2E 测试环境（解决容器化测试/权限验证/前端配置中心依赖问题）、验证业务语义（CI 只验证编译和测试通过，无法验证业务逻辑正确和用户体验）。
Aone 实践

阿里巴巴 Aone 的 Agent-native 研发模式升级

作者向邦宇，阿里 10 年+，负责代码平台和多个 AI Coding 工具（含面向小白的「搭叩」）。Aone 团队做了以下探索：
🔄 研发模式：阶段合并
Coding 阶段同步完成 Code Review + CI 检查。不再按前后端分工，按端到端业务场景组织交付。
📂 All In Code 大库
10+ 个应用全部放一个库：前后端代码、Skills、文档、发布信息、handbook。代码库 = 唯一事实来源。
👥 Agent Teams
人和异构 Agent 始终在同一上下文中讨论。@一个前端 Agent 写前端，人能操作 Agent 军团。
🏠 Claw 管家模式
Agent 作为「公民」：被动接受指令 + 主动巡检（报警排查、资源优化、死代码清理、文档维护）。
🔐 Agentic IAM
核心问题：Agent 由谁负责、谁持有、有什么权限。主体从「人」变为「自主执行的软件实体」。
📋 ChangeSet 理念
存在 Git 版本库中的变更过程记录系统。解决「这次改了哪些文件、需要什么测试、处于什么状态」的承载问题。
ChangeSet

为什么需要 ChangeSet？

分支和 Topic 都不足以表达「一次变更」：
❌ 分支与 Git 强绑定，表达能力有限
❌ Topic 与平台强绑定，表达能力同样受限
❌ 分支本身动态变化，无法回溯原始变更
✅ ChangeSet 记录一次变更从发起到发布的全部上下文，存在 Git 里
合并策略

Agent 时代的代码合并

短生命周期分支 + 合并队列 + 分级质量门禁
• 每个 Agent 任务在独立分支上执行
• 完成后进入串行化合并队列，先完成先合并
• 合并前通过对应级别质量门禁
• 自动处理 rebase 和简单冲突
• 无法自动处理的冲突退出队列，等人
结语
AoneCopilot 项目始于 2023 年。那时还在遥想「一句话完成一个需求」的时代是否终将到来。不过短短三年，那曾经遥不可及的未来已近在咫尺。
"时间仿佛只翻过了几页日历，却又像悄然跨越了一个世纪。"
