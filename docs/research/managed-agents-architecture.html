核心论断

「要扩大 Agent 的规模，就要解耦脑和手」

2026 年 4 月 8 日，Anthropic 发布了一篇关于 Managed Agents 的博客，披露了内部将 Agent 从「单兵作战」推向「蜂群协作」的架构演进。核心结论：你为模型写的修补代码注定会过时，因为模型的进化速度永远比你重构代码的速度快。唯一的破局之道是解耦——把大模型的规划决策能力（大脑）和执行代码的沙盒环境（双手）彻底劈开。
「宠物 vs 牛马」：传统 Agent 架构把模型、记忆和环境死死绑在一起——等于把 Agent 当宠物养。跑错一行配置、记忆越来越多、环境被污染，系统就越来越难用甚至得重装。Managed Agents 告诉你：把 Agent 当牛马用——大脑只管发指令，底层双手全是无状态的独立沙盒。哪个沙盒跑崩了？直接干掉，重新拉起一个干净的接着干。
架构发现

SDK Beta 目录下的六个核心模块

小天通过逆向 Anthropic SDK 的 beta 目录，发现了一整套 Managed Agents 基础架构。六个模块虽然没有具体实现（都是云端 API 的包裹），但从参数和类型定义中可以推断出完整的设计意图：
🤖 Agents
静态模板：定义模型、工具、系统提示词。Agent 是「我是谁」——不承载状态，只承载能力定义。
📦 Environments
无状态沙盒：执行代码的隔离环境。可随时销毁重建，确保双手永不污染大脑。
💬 Sessions
动态状态：对话、线程、记忆挂载。Session 是「我在干什么」——同一 Agent 可跑十个独立 Session。
🛠 Skills
能力扩展：Agent 可用的工具和能力集，通过 Skills 机制动态挂载到 Agent 模板上。
🧠 Memory
持久记忆：Agent 的记忆不附着于 Agent 本身，而是作为 Memory Store 挂载到 Session 上——这又是解耦。
💾 Stores
数据存储：文件、知识库、向量数据库等持久化数据层，与 Agent 和 Session 完全解耦。
关键发现

🎯 Coordinator：不干活的指挥官

📋
唯一职责：拆任务、派活
在 Agent 类的类型定义中，有一个 coordinator 字段——一个不写代码、不做推理的纯调度者
👥
花名册：最多 20 个 Agent
每个 Agent 有独立的 prompt、工具和 MCP 服务器，Coordinator 只管分配不管执行
🔄
天然解决上下文窗口问题
单人做长任务会不断压缩上下文、丢失记忆。多 Agent 编队：一个编码、一个 review、一个测试——各自的上下文保持干净
核心概念

💡 Session 解耦：最重要的设计决策

📝
Agent 是「我是谁」→ 模板
模型 + 工具 + 提示词 = 静态能力定义。Agent 本身不存储任何状态
💬
Session 是「我在干什么」→ 状态
对话、线程、记忆、文件挂载都归属 Session。同一 Agent 可同时跑 10 个独立 Session
⏪
Session 快照：随时回滚「最聪明状态」
Agent 刚搜完代码库时是最聪明的状态。任务做多了会变笨——但 Coordinator 可以保存这个「巅峰状态」，随时克隆复用来应对新任务
范式转移

🐱 宠物 vs 🐂 牛马

传统 Agent = 宠物：模型、记忆、环境死死绑定。配置错一行、记忆越来越多、环境被污染 → 系统越来越难用，甚至得重装。
Managed Agent = 牛马：大脑（决策）和双手（执行）彻底分离。大脑只管发指令，双手全是无状态沙盒。沙盒跑崩了？直接干掉重拉——一个配置导致全盘崩溃在这种架构下根本不可能发生。
核心理由：你为模型写的修补代码注定会过时。模型的进化速度永远比你重构代码的速度快。所以不要修补——要解耦。

技术趋势

☁️ 计算范式的转变

以前云计算是「一个容器固定服务长期使用」。但在 Managed Agents 模式下，未来可能是无数个 Agent 容器在不断地创建和销毁。Docker 容器的启动和销毁延迟在这种场景下成了瓶颈——这也是为什么腾讯 Cube Sandbox（毫秒级沙盒启动）的出现恰逢其时。
计算资源的分配和计价模式也会随之变革：不再是按「容器运行时长」计费，而是按「Agent 任务完成量」计费。云计算的下一个形态，可能是 Agent 原生的 Serverless。
Why This Matters

这跟你有什么关系

你就已经在跑多 Agent 架构。你的 Hermes + Kanban + Ralph Loop 本质上就是 Coordinator + Worker 模式。Kanban dispatcher 拆任务、派活，worker profile 各自执行——这正是 Managed Agents 的协调者思维。
但差距在哪？
· Session 状态管理——你的 Kanban worker 之间共享状态吗？有没有 Session 快照和回滚？
· 沙盒隔离——你的 worker 跑在同一环境里还是独立沙盒？一个 worker 崩了会影响其他吗？
· 规模化——你能同时跑 20 个 worker 吗？上下文压缩是瓶颈吗？
这篇视频不是在讲一个遥远的概念——它在讲你已经在做但还没做透的事。
核心结论

解耦不是选择，是 Agent 规模化的唯一数学解

小天这期视频的核心价值不在于「复刻了 Anthropic 的 SDK」——而在于用实际代码跑通了这套理念：Coordinator 只调度不执行、Agent 模板与 Session 状态分离、沙盒作为无状态执行单元可随时销毁重建。

最重要的警示：当海外厂商已经把 Agent 从「个人工具」上升到「企业基础设施」的时候，国内还在争论 OpenCLI vs Hermes 哪个更好用。这不是工具之争——这是对 Agent 理解维度的差距。Anthropic 的阳谋是做一个云端的 Agent 操作系统，而如果你还在琢磨怎么在本地养好一只 Agent，你已经落后了一个维度。
