核心问题

没有 OS 层的 Agent 框架：每个 Agent 都像没有操作系统的裸机程序

当前主流 Agent 框架（ReAct、AutoGen、MetaGPT、Open-Interpreter）都直接在 LLM API 之上构建，完全缺失 OS 级的资源调度层。当一个 LLM 请求因 GPU 显存不足而崩溃时，框架只能收到一个异常，然后重试——这就是经典的操作系统缺失症状：没有内核来管理硬件资源、调度进程、处理中断。
AIOS 的核心洞察：LLM Agent 需要的不只是更好的 prompt，而是需要一个真正的操作系统内核——封装 LLM 为「CPU 核心」、管理 Agent 为「进程」、提供统一的系统调用接口。这不是类比，而是架构设计。

内核模块

🔲 LLM 核心：把 LLM 封装为「CPU 核心」

🧠
LLMAdapter 统一封装
每个 LLM 实例（云端 API 或本地模型）被封装为一个「核心」，类比 CPU 核心。统一的 LLMAdapter 类屏蔽不同部署方式的差异，系统调用接口标准化
📊
📋 调度器：FIFO 与 Round Robin 双算法
所有队列集中管理。默认 RR（时间片轮转），支持 FIFO。配合 上下文中断机制实现任务暂停和恢复——长任务不会饿死短任务
⚡
关键优化：GPU 显存精确调度
传统做法：prompt → tensor → 加载到 GPU → CUDA OOM → 崩溃重试。AIOS 调度器精确计算可用显存，只在够用时才分配——消除试错开销
内核模块

💾 上下文与内存管理：Agent 的「虚拟内存」

📸
上下文管理器：两种快照机制
文本快照（闭源 LLM）：保存已解码输出。 Logits 快照（开源模型）：保留 beam search 中间状态——粒度更细，恢复更精确
🔄
内存管理器：LRU-K 淘汰策略
管理 Agent 运行时内存（对话日志、工具调用结果）。超过阈值（默认 80%）时 LRU-K 策略将低频数据交换到磁盘（通过存储管理器）
🗄️
存储管理器：文件 + 向量数据库
基于 Agent ID 的持久化存储。本地文件系统 + ChromaDB 向量数据库，支持文件创建、挂载、回滚、共享
内核模块

🔧 工具与安全管理

🔌
工具管理器：动态加载 + 冲突解决
按名称动态加载工具，参数验证。HashMap 实时监控工具实例计数——检测到冲突时自动推进到下一个队列请求
🔐
访问管理器：权限 + 用户干预
基于 Agent ID → 权限组映射的 跨 Agent 数据访问控制。不可逆操作（删除、覆写、权限修改）强制要求用户显式确认
内核接口

📞 系统调用接口

每个系统调用继承 Python Thread 类，多线程并发执行。Agent 查询被分解为分类的系统调用，由调度器分发到各模块队列。
模块系统调用
LLM 核心execute_llm_syscall, get_model_response, process_model_response
调度器execute_syscall, start, stop
上下文管理generate_response_with_interruption, load_context, clear_context
内存管理add_memory, remove_memory, update_memory, retrieve_memory
存储管理sto_create_file, sto_mount, sto_write, sto_retrieve, sto_rollback, sto_share
工具管理execute_tool_syscall, load_tool_instance
访问管理add_privilege, check_access, ask_permission

生态扩展

🦀 Crab · ⚡ rivet-dev/agent-os

🦀
Crab：语义感知的 Agent 沙盒快照
HKUST 出品。eBPF 内核监控 + CRIU/ZFS 检查点。核心发现：87% 的 Agent 回合不产生需恢复的状态——大多数 checkpoint 是浪费。Crab 只对有效状态做快照，开销 <1.9%，100% 恢复正确率
⚡
rivet-dev/agent-os：WASM 内核运行时
JavaScript 写的进程内 OS 内核 + WebAssembly + V8 隔离。6ms 冷启动（vs Docker 440ms，92× 更快），22MB 内存（47× 更少），17× 更便宜。ACP 协议的参考实现之一

下篇 · Agent Sandbox 运行时

🛡️ Agent 的真正问题不是"怎么调用模型"，而是"把不可控执行体放在哪里"

只要 Agent 开始执行代码、操作文件、访问网页、安装依赖、调用系统命令，问题就不再是 prompt engineering，而是一个更底层的工程问题：我们到底要把这个不完全可控的执行体放在哪里？
传统沙箱：解决"不信任代码"的问题。
Agent 沙箱：解决"不完全信任一个会自己规划、自己调用工具、自己产生副作用的系统"的问题。
它既要隔离风险，又要保留足够真实的运行环境；既要启动快、成本低，又要支持浏览器、终端、文件系统、MCP、IDE、Jupyter 等复杂工具链。

第一梯队

🏆 CubeSandbox：生产级性能之王

⚡
冷启动 <60ms · P99 <150ms · 内存 <5MB
CubeAPI → CubeMaster → Cubelet/CubeProxy/CubeVS → CubeHypervisor → KVM MicroVM。eBPF 做网络隔离，RustVMM 构建 MicroVM。E2B API 兼容——降低迁移成本
🎯
适用场景：大规模 Agent 执行平台
多租户代码运行 · E2B 替代或成本优化 · 对冷启动和部署密度极度敏感的生产系统。短板：主要面向 Linux 生产环境，架构较重，需要运行时/网络/集群运维能力

🐳 agent-infra/sandbox：最快能用

把 Browser + Shell + File + MCP + VSCode Server + Jupyter 塞进一个 Docker 容器。不追求最强隔离，追求开箱即用——早期产品最缺的是反馈速度，不是完美架构。

☸️ k8s-sigs/agent-sandbox：K8s 原生

把 Agent 沙箱抽象成 K8s 声明式资源：SandboxClaim → SandboxTemplate → Sandbox → Pod → Runtime。适合已有成熟 K8s 平台的团队——把 Agent 沙箱纳入已有治理体系。

生态组件

🎛️ sandbox-agent：统一 Agent 控制层

通过 HTTP 统一控制 Claude Code、Codex、OpenCode、Amp 等 Coding Agent，输出统一会话 schema。不是底层沙箱，是控制适配层。适合：Coding Agent 平台、多 Agent 对比路由、统一会话审计。

📡 openbrowser + context-mode

🌐
openbrowser：Agent 的浏览器能力组件
封装浏览器自动化，适配 Agent 使用模式。但浏览器隔离 ≠ 系统隔离
📉
context-mode：上下文也是一种"沙箱"

架构分层

🧱 真正落地：四层 Agent Runtime 可组合栈

不建议寻找"一个项目解决所有问题"。现实工程中的 Agent Runtime 架构通常分四层：
🎛️ Agent Control Layer — 统一控制 Claude Code / Codex / OpenCode / 自研 Agent
🔧 Tool Layer — Browser / Shell / File / MCP / IDE / Jupyter
🛡️ Sandbox Runtime Layer — MicroVM / Container / K8s Pod / Serverless Sandbox
🏗️ Infrastructure Layer — Network / Storage / Image / Snapshot / Observability / Policy
项目映射：
控制层：sandbox-agent 浏览器工具：openbrowser 上下文压缩：context-mode 一体化工具：agent-infra/sandbox 底层运行时：CubeSandbox · microsandbox · OpenSandbox K8s 管理层：k8s-sigs/agent-sandbox
参考组合 — 生产级 Coding Agent 平台：
前端产品 → Agent 编排服务 → sandbox-agent 统一控制 Claude Code / Codex → CubeSandbox 提供 MicroVM 执行环境 → openbrowser 提供浏览器操作 → context-mode 控制工具输出进入上下文的粒度 → K8s / 自研调度系统管理资源池
趋势判断

📈 Agent Sandbox 五年趋势

1
MicroVM 成为高安全 Agent Runtime 主流方向
容器不会消失，但在不可信代码、多租户、云端执行场景里，MicroVM 隔离边界更容易解释，也更容易通过安全审计
2
冷启动成为核心竞争指标——<100ms 是合格线
Agent 任务天然碎片化：创建→执行→暂停→恢复→销毁。P99 可控、内存 <20MB、预热池和快照恢复是标配
3
MCP 推动工具层标准化——沙箱不只是"运行代码的地方"
浏览器、文件、数据库、CI、代码编辑器等通过 MCP 统一暴露。沙箱成为"托管工具能力的边界"
4
上下文管理成为运行时的一部分——隔离信息流
Agent 时代不光隔离 CPU/内存/文件/网络，还要隔离信息流：哪些工具输出进入模型上下文？哪些只进审计系统？
5
生产平台走向组合式，不是单体式
MicroVM 负责安全执行 + K8s 负责资源管理 + MCP 负责工具协议 + Agent 控制层负责会话事件 + 上下文层负责信息压缩 + 可观测性负责审计回放

Why This Matters

你的 Hermes + Kanban 在 AgentOS 光谱的哪个位置？

AIOS 的架构和你已经在做的多 Agent 编队不是两回事——它们是同一光谱上的不同点位。

你已经有的：Kanban dispatcher ≈ AIOS Scheduler（任务分解和派发）· Ralph Loop ≈ Context Manager（多轮状态管理）· worker profiles ≈ LLM Core 的多核抽象 · Hermes skill 系统 ≈ Tool Manager。

AIOS 做得更深的地方：GPU 显存的精确调度（你依赖 Claude Code 的 API，但如果是本地模型这就是硬需求）· 统一的系统调用接口（你的 Kanban worker 之间目前通过文件传递状态，没有标准化的 IPC）· 内存 LRU-K 交换（你的长任务上下文压缩是粗粒度的，没有细粒度的冷热数据分离）。

最直接的借鉴：Crab 的语义感知快照——87% 的 Agent 回合不需要 checkpoint。如果你的 Kanban worker 也能识别哪些回合产生了持久状态变化、只对这些回合做快照，你的 worker 恢复效率能提升一个数量级。
