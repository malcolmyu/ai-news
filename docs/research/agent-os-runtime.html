核心论断

当问题形状变了，答案就不能还是 prompt

作者追溯了一条清晰的认知升级路径，最终指向一个结论：Agent 系统的核心问题，正在从「怎么让模型更聪明」转向「长期任务如何可靠执行」——这不是 prompt engineering 的范畴，而是 OS / Runtime / 分布式系统的问题。
1
第一层：Prompt 为王
早期以为核心在 prompt —— 怎么让模型更会拆任务、更稳地调工具、遇到错误还能往前走。
2
第二层：Workflow 才是麻烦
复杂任务有文件读写、命令执行、API、状态和重试。于是有了 harness、tool loop、memory、planner。
3
第三层：Runtime 才是地基
Workflow 跑在哪里？状态放哪里？失败怎么恢复？凭证属于谁？上下文满了什么能丢？—— 这时候事情开始像 Operating System。
01 · 最危险的架构问题

Harness 会腐化 —— 过期的正确性比 bug 更可怕

什么是 Harness 腐化？ 不是代码写烂，而是慢慢堆满某一代模型、某一代工具、某一种部署环境的假设——模型快顶满窗口加 context reset，模型不会从错误恢复加 retry prompt，sandbox 偶尔卡死加 watchdog。每个补丁加的时候都合理。
为什么比 bug 更危险？ 模型进步太快——今天像缺陷的行为三个月后可能不是了，今天好用的 prompt trick 下一代可能反而被干扰。Harness 里最危险的是 过期的正确性：它曾经对过、救过线上，所以没人敢删；等底层模型变了，它就变成看不见的阻力。
类比：这和 kernel workaround、某代 NIC 行为、某版 GPU scheduler、某云厂商限制很像——先是补丁，再变成 ABI 的一部分，最后谁都不敢动。Agent harness 也会这样。
02 · 关键洞察

Context Window is NOT Runtime

当任务长时间跑起来，context engineering 不只是「怎么喂模型」，而是状态管理。上下文窗口只是当前调用能看到的一小块工作集——它不是 runtime，不是 session，更不是 source of truth。
类比：模型上下文更像 CPU cache 或进程当前映射进来的页——影响很大，但不能承担持久状态。如果系统把 context 当 session，恢复能力基本是假的——恢复的往往是被压缩、被转述、可能已经偏掉的故事版本。
03 · 解决方案

Append-Only Session Log ≈ Event Sourcing

把完整 session 当成 append-only log：发生过什么就记下来，模型当前需要什么再从 log 构造 view。这和分布式系统里的 event sourcing 一模一样——存事件序列而非当前状态，状态可重放，不同视图可从同一份 log materialize。
隐含红利：把「记忆」从模型里拿出来——runtime 存事实，模型在某个 view 上推理。边界很像数据库与查询引擎：数据别塞进查询计划，计划可以变，数据不能丢。
04 · 架构分离

Brain vs Hands = Control Plane / Data Plane

「把大脑和手拆开」的直觉很直观，作者把它映射为 control plane 与 data plane 的分离——这是云基础设施走了二十年的路。
角色类比职责
Brain（模型 + harness）Control Plane决策、编排、选工具、定下一步
Hands（sandbox/tool/MCP）Data Plane真执行、跑命令、访问资源、产生副作用
生命周期不同：Control plane 要可恢复可升级；Data plane 要隔离可丢可按需起；Session state 要比二者更持久；Credentials 又应在另一道边界。全塞一个盒子里，短期省事，长期全是耦合。

05 · 执行环境

Tools & Sandbox → Disposable Runtime

Sandbox 不是家、不是记忆、不是长期状态——它是某次执行的工位。需要时 provision，坏了就丢，污了就换。设计目标应是 靠 runtime 恢复任务，而不是抢救某个容器。
连锁效应：一旦 tools/sandbox 都是 disposable，orchestration 自然更像 control plane——不关心某个 sandbox 的「感受」，而关心任务需要什么执行能力、有没有健康实例、失败后如何重试、副作用是否已发生。
06 · 架构原则

Interface 比 Implementation 更重要

文章反复强调的不是某段 harness 怎么写、某个 sandbox 怎么实现——而是 session、execute、wake、provision 这类边界。很像 OS 的 syscall：harness 调 execute，不必知道背后是容器、VM、MCP 还是未来设备。
接口稳定，实现才能乱换。关键不是抽象癖，而是未来真的会乱换——模型、harness、工具协议、sandbox 类型、部署形态都会换。押注具体实现，很快被拖住；押注稳定接口，下层可以演进。
07 · 未解决的问题

Long-Running 的可靠性、观测和评价 —— 都还没被吃透

⚠️ Long-Running Reliability
Demo 很顺，但真正难的是长期可靠性——模型失败、工具超时、sandbox 崩、网络抖、权限过期、用户插话都会发生。动作有没有副作用？重试会不会双提交？改文件与调 API 之间有没有一致性？两个 Agent 同时改同一 repo 谁仲裁？这些问题全是老派分布式系统的问题，只是入口换成了 Agent。
🔴 Observability Gap
传统服务有 logs、metrics、traces。Agent 系统要看 token、tool calls、session events、中间决策、compaction 前后丢了什么。评价也不能只看最终答案——是否走了危险路径、是否滥用权限、是否在不确定时装确定。这需要 runtime 层面的观测，不是最后扔给另一个模型打个分了事。
08 · 收束

Mental Model 转变：从模型出发 → 从 Runtime 出发

以前习惯从模型能力出发——模型越强，Agent 越强。现在更愿意从 Runtime 出发：模型是 brain，但 brain 需要运行时——手、记忆、权限边界、恢复、观测、调度。这些不能与某一代 brain 绑死，否则每次模型升级都是一次痛苦迁移。
当 Agent infra 进入系统工程阶段，核心问题会慢慢从「怎么让模型更聪明」转向更不性感但决定能不能长大的那一类：状态模型是什么？控制面与执行面怎么分？失败恢复靠什么？哪些接口要长期稳定？什么绝不能只活在上下文窗口里？
📌 6 条收束趋势（作者判断）
1. Context Window 不是 Runtime
上下文只是 CPU cache，不能承担持久状态。模型需要什么就从 event log 构造 view。
2. Harness 不该变成历史补丁博物馆
过期的正确性比 bug 更危险。Harness 是策略层，不是地基。
3. Session Log 会越来越像系统事实源
Append-only event stream，可 replay、可 diff、可审计、可 materialize 不同视图。
4. Tools & Sandbox 会越来越 Disposable
不是家、不是记忆——是工位。Provision → Use → Destroy，靠 runtime 恢复而非抢救容器。
5. Orchestration 会越来越像 Control Plane
Brain（Control Plane）与 Hands（Data Plane）分离，生命周期独立管理。
6. Interface 会比 Implementation 更值钱
定义稳定接口（execute / provision / wake / session），实现可以乱换。
Why This Matters

Hermes Agent 已经在走这条路

这篇文章不是在讲未来——它描述的方向在 Hermes 的架构里已经有对应物。不是在追趋势，而是在验证架构决策的正确性。

📝 Append-Only Session Log

Hermes 的 session_search 就是 append-only event stream 的雏形——记录每一次对话、每一次工具调用、每一次决策。可检索、可回放、可审计。

差距：目前是 search-only，还没有变成 runtime 的 source of truth——compaction 策略、上下文 materialization 仍需手动干预。

🔧 Skills = Replaceable Harness

Hermes 的 skill 体系天生就是「harness 不是地基」的实现——每个 skill 是可插拔的策略层，模型升级时 skill 可以独立更新，不会和底层模型绑定。

差距：Skill 的相互影响、冲突检测、过期自动标记还不够系统化。

🎛️ Control Plane / Data Plane

你的「主 Agent 只协调不写代码」规则，就是 control plane 和 data plane 分离的实践。delegate_task 和 kanban 体系让 Brain（规划/编排）和 Hands（执行/写代码）在不同上下文运行。

差距：Data plane 还不够 disposable——sandbox 挂了需要人工介入。

🔌 Stable Interface

Hermes 的 tool abstraction layer（terminal、browser、file、search）定义了统一接口——底层是本地、远程还是容器，对 harness 透明。

差距：Tool 的 availability 和 capability 目前靠静态声明，缺少运行时 negotiation。
Key Takeaway

真正值钱的不是某一个 Agent，而是承载 Agent 的 Runtime

单个进程重要，但 OS 更重要。单个服务重要，但 Cloud Runtime 更重要。单个模型当然重要，但当模型够多、任务够长、工具够复杂时，谁能定义那层稳定的运行时抽象，谁才可能在搭下一代基础设施的地基。

Agent infra 的争论，会从 prompt、memory、tool use，慢慢滑回更老派的一组词：调度、隔离、一致性、恢复、观测、权限、评估。听起来一点都不新——系统工程常常就是这样：新 workload 先兴奋于能力，能力进生产后，老问题全回来。只是这次，执行主体从人写的程序，换成了会推理、会调工具、也会犯奇怪错误的模型。
