Loop Engineering 与管理升维：从一线执行到二线架构

2026 年 6 月 AI Agent 领域涌现的 Loop Engineering 思潮，与一线管理者晋升二线管理者的认知迁移高度同构。
这篇不讨论 Agent 怎么写代码。讨论一个人从「亲手做管理」到「设计管理系统」的过程中，什么样的问题会反复出现。

01 · 起源

Boris 删了 IDE，你什么时候删了「亲自管」？

2026 年 6 月 8 日凌晨，Peter Steinberger 发了一条推，650 万浏览。两句话：
You shouldn't be prompting coding agents anymore.
You should be designing loops that prompt your agents.
几天后，Claude Code 负责人 Boris Cherny 在 WorkOS 访谈里讲了更具体的事：他在 2025 年 11 月删了 IDE，之后 30 天 259 个 PR 全是 Claude Code 自己写的。他的工作从写代码变成了写 loop——让 Agent 自己去读 GitHub、读 Slack、读 Twitter，自己决定要做什么。
01 · 翻译

这不是 Agent 的问题。这是你的问题。

把「Claude」换成「你的 -1 管理者」。Boris 那句话不需要改一个字：
我不再 prompt 我的 -1 了。我设计了 loop，loop 去 prompt 他们、读结果、判断完成没有。我的工作是写 loop。
Loop Engineering 和管理升维的重叠不是巧合。它们面对的是同一个结构性问题：当你的杠杆从「亲手做」迁移到「设计系统让别人做」，所有架构问题都会重新出现一次。
02 · 三层抽象

Prompt → Context → Loop：你卡在哪一层？

层Agent 工程管理阶段你在优化什么
Prompt Engineering手写指令，逐轮调教一线管理者（管执行）给每个人的具体指令质量
Context Engineering管上下文窗口：文档、历史、工具成熟一线（管节奏）信息流、对齐机制、决策背景
Loop Engineering设计自运行系统：触发→执行→验证→迭代二线管理者（管管理者）系统能否在你不在场时运转
Prompt Engineering 阶段：你的杠杆来自你会不会下指令。你把话说清楚，下面的人做对了——这是「prompt 调优」。你活在每一个 1:1 里、每一个异常的第一响应里。
Context Engineering 阶段：你发现单条指令有天花板。你建文档、定流程、设对齐机制。你开始从「我说什么你做什么」转向「你知道背景，你来判断」。
Loop Engineering 阶段：你的 -1 自己成了管理者。你不能逐条 prompt 他们——他们需要自己 prompt 自己的团队。你设计的是让他们能在里面运行的管理回路。一线优化自己说的话。二线优化别人说话时能不能说对。
03 · Building Blocks

五个建筑块 + 记忆：Loop 的骨头

Lushbinary 和 cobusgreyling 的仓库把循环拆成五（加一）个建筑块。每个都能直译成管理场景。
Block 1

Automations — 管理节律

Loop 的心跳。定时触发，发现工作，不靠你主动问。
1
-1 和他们的团队有固定 1:1 节奏
你参加但不主持。节律不依赖你在场——你不在它照样跑。
2
异常升级有既定触发条件
「超过 2 周未解决」自动上浮至你。不需要你巡视。
3
季度 OKR review 由 -1 拉通
你只审不推。loop 不能每次靠你手动启动。
如果每次都要你主动问「最近怎么样」——那不是 loop，是你在手动 prompt。
Block 2

Worktrees — 边界与所有权

并行执行不互相踩。两个 Agent 写同一个文件 = 两个管理者在模糊地带同时发力。
1
这个业务线归 A
B 有更好的想法也要 A 拍板。边界写在纸面上，不在默契里。
2
跨团队项目有主责人和配合方
配合到什么程度有书面约定。模糊时仲裁权在你这里。
3
边界越早划清
后续越少处理「他俩谁说了算」的冲突。Worktree 是跑之前就要搭的。
Block 3

Skills — 管理知识外化

写下来。Agent 不用每次猜你的规范。你的 -1 不用每次靠你亲自讲。
1
管理 Playbook
第一次面对团队冲突、绩效面谈、跨部门撕扯时看什么？不是靠你口述。
2
决策框架
「技术债 vs 新功能」这种 classic 取舍，你的 -1 知不知道你是怎么做判断的？
3
失败案例库
每踩过一个坑，写三行：「当时情况 + 我做了什么 + 为什么错了 + 该怎么做」。这就是管理的 SKILL.md。
Block 4

Connectors — 接口与人脉

Agent 接入已有工具链。你的 -1 需要往上（你）、横向（peer）、往下（自己团队）的通路。
1
跨部门协调不靠你背书
-1 能自己对接 peer，不每次都拉你进来站台。
2
对上汇报知道你的节奏
知道你什么时候要细节、什么时候只要结论。
3
组织障碍知道找谁解
不卡在你这里。差 connector 让你变成瓶颈。
Block 5

Sub-agents — 执行与验证分离

Loop Engineering 最核心的原则。写代码的和检查代码的不能是同一个人。
你的 -1 做了某个决策，你不能让同一个人评价「这个决策对不对」。你需要独立的验证层：其他 -1 的交叉 review、你设计的 check 机制、数据指标。A 既管交付又汇报交付质量 → 你会得到永远在进步的虚假叙事。
Claude Code 的 /goal 命令在每轮之后跑一个 verifier model 检查是否 done。不是「你觉得做完了吗」，是「测试真绿了吗」。管理里就是：不是「你觉得团队好吗」，是「attrition 率、skip-level 反馈、交叉 review 数据说了什么」。
+ Memory

持久的管理记忆

Agent 会忘。Repo 不会。状态活在磁盘上，不活在 context window 里。
人比 Agent 更会忘。上次 1:1 聊了什么、三个月前的绩效面谈结论、团队成员的成长拐点——不写下来，它们只活在你大脑的上下文窗口里。窗口清空那天，信息就丢了。
最小可行方案：每次 1:1 后各写三行摘要，存共享文档。绩效周期后核心判断写进持久库。组织级决策的上下文（当时为什么这么做）跟决策结果一样重要。这就是管理的 STATE.md。
04 · 验证体系

让系统自己说「不对」，而不是靠你巡视

@mosyaseen 在 Steinberger 那条推的回复被公认是 loop engineering 最核心的一条警告：
Designing the loop is half of it. The other half is putting something in the loop that can say no: a test, a type check, a real error. A loop with nothing to push back is the agent agreeing with itself on repeat.
管理版直译：一个没有验证层的 -1 管理者，在长期运行中会逐渐把自己的判断当成事实。这不是人品问题——这是结构问题。只要执行者和评价者是同一个人，这个结果几乎必然出现。
验证维度具体机制周期
定量门禁attrition 率、promo 率、项目 on-time 率。异常自动浮现，不等季度 review月
Skip-level每季度和 -1 团队做 1:1。不问「你老板怎么样」，问「你最近三个月最大成长是什么」「你最想改变的一件事」季度
交叉验证两个 -1 交叉 review 各自团队 OKR 达成。让 peer 评价，不只是你评价季度
成长观测-1 在下属出问题时第一反应是「我来修」还是「让 TA 自己修」？-1 能不能在你不给答案时拿出 2-3 个方案并分析取舍？半年
05 · 分级授权

L1→L2→L3：新 loop 不能直接上全自动

cobusgreyling 的 pattern picker 有一个设计原则：新 loop 从 L1（只报告）起步，验证可靠后升 L2（辅助执行），最终到 L3（全自动）。直接上 L3 的 loop 几乎一定会炸。管理升维完全一样。
阶段时间你在干什么你在验证什么
L1 · 观察与报告3-6 个月重大决策你拍板。TA 汇报「发生什么 + 打算怎么做 + 为什么」。你 shadow 但不主持TA 的判断跟你差多远？信息不全时追问还是硬猜？冲突是回避还是处理？
L2 · 辅助决策6-12 个月TA 自主做大部分决策。跨团队、预算、敏感人事需提前同步你。OKR 你来审但不改TA 的决策质量在你不在时是否稳定？团队没有你 direct involvement 能否运转？
L3 · 自主运行12 月+全权负责。你只做 ADR 级干预（方向偏差、重大风险）。TA 开始 mentor 更一线管理者TA 有没有从「管执行」升维到「管管理者」？TA 有没有开始设计自己的 loop？
06 · 失败模式

Loop 会怎么炸，管理就怎么炸

Loop Engineering 材料里记录了四类典型失败。管理场景翻译过来一模一样。
失败 1

无验证的循环自洽

Loop 版：Agent 每次认为自己完成了任务，因为没东西能说「不对」。
管理版：-1 汇报永远是「进展顺利」，你听完觉得问题不大，三个月后发现项目已偏航。
解法：定量指标 + skip-level + 交叉 review，三者至少有其二。
失败 2

Comprehension Debt

Loop 版：你越来越不了解 loop 到底做了什么，只看它说完成了。
管理版：你不再理解 -1 团队里的实际情况，只满足于「管理管理者的报表」。
解法：定期 skip-level、参与关键 review、保持你自己的技术/业务判断力不退化。
失败 3

过度自动化

Loop 版：L3 全自动跑一周，回头看合了 15 个有问题的 PR。
管理版：一切交给 -1，三个月后回来发现团队文化已偏，组织架构被你不在时做的人事决策锁死。
解法：永远保留「降级回 L2 甚至 L1」的机制。自动化可逆，管理信任受损后很难修。
失败 4

Harness 腐化

Loop 版：当年写 loop 时基于某个模型的假设，模型升级后假设不成立了，loop 还在按旧逻辑跑。
管理版：你对 -1 的判断基于半年前的 TA（刚晋升时的冲劲、当时的团队规模）。TA 和团队都在变。你还在按旧印象管理 TA。
解法：每季度重新校准。你对每个 -1 的 mental model 和 TA 本人同步更新。
07 · 核心迁移

从「做管理」到「设计管理」

一线管理者最容易被困住的事情：把管理等同于「做管理的事」——开会、分配任务、解决冲突、做绩效。这些事情真实，但它们是运行一个已经继承的 loop，不是设计一个更好的 loop。
二线管理者的区别不在权力更大或管得更宽。在于视角：
一线问二线问
这个任务谁来做？怎么做好？什么样的系统能让做这件事的人自己做出好决策？
我搞定了 / 我说服了 / 我救了火我不在场，他们自己搞定了
成就感来自直接干预的结果成就感来自系统运转的可观测性
这个迁移的痛苦在于它剥夺了你最熟悉的正反馈来源。Boris 删了 IDE 之后再也没写过一行 Claude Code 的代码。他的成就感从建造转向设计建造系统。你越成功，你越觉得自己可有可无——这既是目标，也是代价。
08 · 长期共事

在长时间运行中判断一个人是否适合做管理者

这就是一个 loop 的长期验证过程。你不能在一次绩效周期里下结论，就像不能跑一次 loop 就判断它能不能上 L3。
观察维度看什么周期
决策质量没有你输入时，TA 的决策跟你预期差多远？季度
自我修正TA 发现自己的决策出问题后，是掩盖还是主动校准？关键节点
放大效应TA 的团队状态是 TA 个人品质的放大还是稀释？半年
管理意愿TA 是享受「带人成长」还是更享受「自己解决难问题」？持续
向上管理TA 报喜还是报真相？把你的话当指令还是输入？每次 1:1
指点的分寸：给 -1 指点时，不能像指导执行者那样「告诉 TA 怎么做」。TA 的工作就是自己判断。你的指点该像 loop tuning——不是「你该这样管」，而是「上次你那样管之后，团队里发生了什么？你观察到什么？」不是「你的问题是 X」，而是「团队在 X 维度的数据/反馈是这样的，你觉得这说明什么？」目标不是让 -1 做出跟你一样的决定，而是让 TA 自己的决策回路变强。
09 · 收束

八个通用问题

二线管理不比一线管理更高级。它是把管理从操作升维到架构。Loop Engineering 提供了一套恰好可以平移的词汇——不是因为两个领域偶然相似，而是因为任何从「亲手做」升维到「设计系统让别人做」的迁移，都必然面对同一组问题：
1
怎么从单次干预升级为定期触发？
Automations
2
怎么保证并行运转时不冲突？
Worktrees / 边界
3
怎么让知识沉淀而非每次都重新解释？
Skills
4
怎么让接口通畅而非拥堵在你这里？
Connectors
5
怎么让执行和验证分离？
Sub-agents + verifier
6
怎么让状态持久而非随人脑遗忘？
Memory / STATE.md
7
怎么在长期运行中防止腐化？
定期重新校准
8
怎么让系统自己说「不对」？
可验证性体系
这八个问题的答案，构成了一个 loop。也构成了一个二线管理者的日常工作。
