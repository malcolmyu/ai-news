OpenSpec：规格驱动开发如何让 AI 不再「做偏」

Vibe Coding 的核心矛盾

Vibe Coding 看起来爽——一句话让 AI 写出整个功能。但需求没说清楚，模型就会「做偏」。这其实对个人的逻辑能力和表达能力要求极高。SDD（规格驱动开发）在入口处加了一道闸门：先对齐需求，再写代码。不是泛泛地说「要做什么」，而是细致到每个功能的规格。
定位

OpenSpec 是什么

一个轻量级 SDD 框架，通过提示词注入让 AI 严格按规格开发。与 GitHub Spec Kit（重）、Kiro（绑定 IDE）不同，OpenSpec 走轻量灵活路线——不绑定模型、不绑定工具、不强制阶段门槛。npm 全局安装，25+ 工具支持，MIT 开源。
工作流

四步核心流程 — 从想法到归档

1
Explore — 需求探索（强烈推荐）
你说「帮我做一个 AI 对话机器人」，AI 会反过来问你：用什么前端？什么模型？什么架构？要不要对话历史？要不要流式输出？把思考外包给 AI，不用一开始就想清楚。UP 主评价：「这个指令是我最喜欢的，他的提问更全面，经常会让我觉得——这个问题问得好，我咋就没想到呢。」
2
Propose — 生成规格文档
AI 自动创建 3 个文档 + 1 个文件夹：proposal.md（为什么做）、design.md（怎么做）、specs/（每个功能的详细规格，用「当…则…」结构化句式）、tasks.md（开发计划清单）。UP 主评价：「好的文档是把开发者变成无脑的执行机器，拿到文档就能干活。OpenSpec 基本做到了。」
3
Apply — 执行开发
AI 读取 tasks.md 中的任务清单 + 相关规格文档，逐步执行开发。视频中演示项目 7 分钟跑完，AI 自己完成测试并截图验证。完成后在 tasks.md 中逐项打勾标记进度。
4
Archive — 智能归档
归档做两件事：① 将当前任务文件夹移入 archive/（保留历史轨迹）；② 将 specs/ 合并到全局 Specs 文件夹，执行增删改三种操作——新功能直接复制、已有功能新增场景则在原文中插入段落、已有功能修改则直接改写原段落。结果：archive/ 保留每次变更全貌，Specs/ 始终保持项目最新功能描述。
核心原理

三层架构：Skill 管流程，CLI 生成指令，schema.yaml 定义文档

起初以为 OpenSpec 只是一堆 skill/command 文件，深入后才发现它的设计远比表面复杂。它把工作流控制和文档定义完全分离：
Skill 层（工作流）
只维护基本流程——explore → propose → apply → archive。不记录要写什么文档、怎么写。
CLI 层（动态指令生成）
AI 执行 CLI 命令后，后端程序从配置文件中组合信息，动态生成文档撰写要求（JSON 格式）。包括：要读什么依赖文档、用什么模板、有什么注意事项。
schema.yaml（文档体系定义者）
整个框架的核心。 artifacts 字段决定生成哪些文件，每个文件有 template（模板路径）、instruction（撰写指导）、requires（依赖文档，决定撰写顺序）。默认顺序：需求文档 → 设计方案+功能规格（并行）→ 开发计划。
对比

vs 其他方案

vs Spec Kit (GitHub)
重、阶段门禁严格、Python 环境。OpenSpec 更轻。
vs Kiro (AWS)
强但绑定 IDE 和 Claude。OpenSpec 不绑定工具。
vs 无规格
模糊 prompt → 不可预测结果。SDD 增加可预测性。
自定义

搭建自己的文档体系

执行 openspec schema init 复制默认 schema 到项目。然后：① 修改 schema.yaml — 增删文档、调整顺序；② 修改 templates/ 下的模板 — 调整章节标题和撰写要点；③ 在 config 中切换到新 schema。操作简单，难的是想清楚你的文档体系要长什么样。
注意：如果你删掉了 Specs 文档，模型就不会输出功能规格，归档时也无法将新功能和历史功能整合 —— 这会丢失 OpenSpec 最核心的增量文档管理能力。
配置

全局上下文注入

schema.yaml 之外还有一个 config 文件，可写入全局要求：项目背景、技术选型、文档风格、语言偏好等。AI 撰写所有文档时都会参考这段 context。还可以针对每个文档写个性化要求——比如要求 proposal.md 控制在 500 字符以内。

核心观点

SDD 不会随模型升级而消失

「AI 会看文档，你不看没关系」

视频结尾的洞察：「在真实世界里，你接触到的开发者基本上不看文档。在数字世界里，AI 可是听话多了。」即使你懒得读规格文档，让 AI 先产出文档再开发，质量也会显著提升——因为 AI 在后续开发中会参考这些文档。

「Token 成本是划算的」

不要以为 SDD 只是多消耗 token 和时间。相比需求不明确造成的反复折腾和方向跑偏，前置投入是非常划算的。需求对齐是整个开发流程中 ROI 最高的环节。

「模型变聪明，但不会读心」

SDD 不会因为模型升级而消失。模型会变强，但它依然需要明确的输入——它不会自动知道你想要什么。SDD 解决的是「需求表达」问题，不是「模型能力」问题。

「SDD + TDD 组合使用」

UP 主提到他经常把 OpenSpec 和 Superpowers 结合使用——SDD 在入口约束需求，TDD 在出口管控质量。两者不是对立的，组合使用效果最好。
与你的场景

Harness 研发体系 + OpenSpec：规格驱动如何嵌入 Agent 工作流

当前场景：Agent 模式下的需求对齐缺口
你在做 Harness 移动端 AI-native 研发体系，Agent 自主修复+验证，人只做架构决策和验收。但 Agent 在执行长程任务时，需求可能漂移——这正是 SDD 解决的「目标漂移」问题。在 Agent 开始执行前注入规格文档，可作为任务执行的锚点。
OpenSpec 的三层架构 ↔ Hermes 的 Skill + Memory 体系
OpenSpec 的 Skill（流程）/ CLI（动态指令）/ schema.yaml（文档定义）三层分离，与 Hermes 的 Skill（工作流）/ Memory（持久状态）/ Tool（能力边界）三层的设计哲学高度重合。尤其是 schema.yaml 的「文档依赖链」概念，可以借鉴到 Hermes skill 中——让 skill 声明自己依赖的前置 skill 和产出物。
归档机制 ↔ 长程任务的增量记忆
OpenSpec 的 archive/（历史全貌）+ Specs/（当前最新）双轨制，对应了 Agent 记忆系统中「短期任务轨迹」和「长期规范对齐」的分层。这种「保存每次变更 + 维护当前最新状态」的模式，正是 Harness 面试考点中 Memory 机制的「局部更新与溯源」需求的工程实现。
