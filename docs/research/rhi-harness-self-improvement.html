01 · Core Problem

Model–Harness 协同演化中的瓶颈

论文提出了一个关键框架：AI 能力的进步不止靠更大的模型和更多的训练计算，更来自 foundation model 与其 harness（推理脚手架）的协同演化。
这个协同演化形成一个递归循环——固定基础模型 → 更强的 harness 组织更有效的 agent 工作流 → 产生高质量 execution traces → 作为训练数据训练未来的基础模型 → 循环。在这个循环中，harness 不只是「用模型」的方式，更是「为模型产生训练数据」的工厂。
但现有 harness 优化方法（Meta-Harness、AFlow、DSPy 等）都是 population-based search——每多一个候选 harness 就需要一次完整的 black-box agent 执行和评估，计算复杂度 Θ(m²)。对于日常用户持续为多个任务优化 harness，这个成本不可承受。
02 · Method

RHI 算法：Trajectory-Local 松弛

RHI 的核心创新是把优化目标从全局比较松弛为局部自比较。每轮只把当前 harness 的输出与上一轮输出（已缓存）做一次 pairwise 比较，而非与整个候选种群对比。
三步闭环：
① Agent 用当前 harness Hⁱ 求解任务 → 得到 outputⁱ
② Evaluator 对比 outputⁱ vs 上一轮 outputⁱ⁻¹ → 产生偏好信号
③ Harness Optimizer 根据 (Hⁱ + 累积偏好历史 D) 生成 Hⁱ⁺¹
关键设计：每轮只需 1 次 agent 执行 + 1 次 pairwise 对比（Θ(1)），而现有方法需要 Θ(m²)。偏好历史 D 压缩了所有先前比较的信息，作为「动量语义信号」防止优化震荡。
Harness 的结构化定义
RHI 把 harness 分解为四个组件，优先优化 contract 和 hop：
组件含义优化优先级
RoleAgent 的角色定义低
InstructionAgent 的行为指令中
ContractAgent 间通信接口规范（传什么信息）高
Hop工作流控制结构（谁在什么时候做什么）高
Harness 表示为 prompt 级别的文本规范（含候选 agent 列表 + 工作流 + 辅助规则），直接拼接到任务 prompt 前注入 black-box agent。无需改代码、无需重新部署。
03 · Experimental Results

三条核心发现

Claim 1：2-3 轮 RHI 超越系统级 test-time scaling

Base ModelRHI 迭代击败对象赢率
Sonnet 4.6 (high)2 轮4.6-max20/30
Opus 4.7 (high)仅 1 轮4.7-xhigh + 4.7-max显著超越
Opus 4.8 (high)2 轮4.8-xhigh / max / ultracode 全家桶全面超越

Claim 2：性能提升 ≠ 更长输出

RHI 的性能提升不伴随 output token 增加（保持在 baseline 1.4-1.8x 的恒定区间）。输出 token 几乎不变，说明 RHI 不是简单的「多写几行代码」，而是更好地组织了 agent 的思考和工作流。

Claim 3：成本效率大幅提升

对比成本节省Cache Read/Write 节省
Sonnet 4.6 RHI[2] vs max-7%-33%
Opus 4.7 RHI[1] vs max-18%-37%
Opus 4.8 RHI[2] vs ultracode-60%-64%
成本节省来自更高效的上下文管理——RHI 学习到的 contract 指定了 agent 间应传递什么信息，避免了全量交互历史的冗余传播。这在概念上类似于在 harness 层面学习一个任务特定的稀疏通信模式（类比 sparse attention）。
04 · Ablation Studies

什么在驱动性能提升？

Harness 组件演化分析

通过 embedding + t-SNE/UMAP 投影和余弦相似度分析，发现 contract 的 task-dependent clustering 最清晰——说明最大的语义变化发生在 orchestrator-subagent 信息接口上。Contract 在 2-3 次迭代后快速稳定（cos similarity 从 0.48 → 0.72），而 role 变化最慢。

内置 Multi-Agent 是纸老虎

论文在 Q&A 做了额外实验，对比四种执行设置：
SettingEloCost
single(default) — 无任何 harness中低
multi(default) — Claude 内置 "create agent team"更低更高
multi(ours) = 显式 harness H⁰最高更低
Claude 内置的 multi-agent 功能不仅没提升反而降低了性能（Elo 更低，成本更高）。只有配上显式的 harness 设计才能逆转。这证明了prompt-level harness 可以超越系统级方案。

RHI 不能替代训练时扩展

实验显示 RHI 可以让较弱的 Sonnet 4.6 接近但无法稳定超越更强的 Opus 4.7。RHI 和更强模型是互补关系——可以先在廉价模型上用 RHI 打磨 harness，然后切换到更强模型获得叠加收益。
05 · Implicit Optimization Hypothesis

RHI 隐式优化了什么？一个信息论假说

虽然 RHI 没有显式的 scalar reward，但实验表明其更新轨迹遵循可预测的模式。论文提出了信息论假说：
"RHI 的隐式目标 = 最大化 contract/hop 与任务的互信息（让信息流组件编码更多任务知识）− 惩罚 harness 组件间的条件冗余（防止各组件重复编码相同信息）。"
实证证据：
指标趋势 (迭代 1→4)
I(contract; task) — debiased↑ 0.99 → 1.34 nats
I(hop; task) — debiased↑ 1.96 → 2.54 nats
I(role; task)↓ 0.47 → 0.33 nats
TC(role,instr,cont,hop | task) — debiased↓ 4.84 → 3.63 nats
这说明 RHI 在让 contracts 和 hops 更加任务特定的同时，减少了不同组件之间的信息冗余——每个组件各司其职，不重复编码相同信息。
06 · Practical Takeaways

核心结论与迁移启示

🔑 Harness-as-Prompt 可行

不用写代码，纯文本 harness 就能超越系统级方案。把 harness 当作可优化的 prompt 变量而非固定代码。

🎯 优先改 Contract 而非 Role

Agent 间的通信接口（传什么信息）是最大杠杆点。反复调整角色描述远不如明确「谁把什么信息传给谁」。

🔄 自比较信号足够

不需要 benchmark、不需要人工标注。昨天自己的输出就是最好的基线。Pairwise 偏好即可驱动有效优化。

💰 稀疏通信降成本

精心设计的 contract 可以显著减少 context 传递量，cache read/write 降 33-64%，直接降低 API 成本。

⚖️ 与更强模型互补

先在小模型上打磨 harness，再切换到更强模型获得叠加收益。RHI 不会让弱模型秒变强，但能让每个模型用得更充分。

⚠️ 内置系统不一定更好

Claude 的 "create agent team" 反而是倒退。显式结构化的 prompt-level harness 比黑盒系统方案更可控。
07 · Limitations & Caveats

局限与未解问题

① 合成 benchmark 的代表性：30 个合成任务覆盖三个领域，但与真实世界的 open-ended coding 仍有差距。所有任务都是结构化研究任务，有明确的 deliverables。
② 单模型族测试：仅验证了 Claude 家族（Sonnet 4.6 / Opus 4.7 / 4.8），未测试 GPT、Gemini 等模型。跨模型泛化性待验证。
③ Harness optimizer 开销未计入：每次 harness 更新需调用 LLM 生成新版本。这部分成本在成本对比中未详细分析。
④ 信息论假说是相关性非因果性：embedding-based 估计的 mutual information 和 total correlation 是代理指标，不能证明 Lharness 内部真的在优化这些量。
⑤ 只完成了循环的前半段：论文只验证了「harness 改进 → 产生更好 traces」，后半段「traces → 训练更好的 foundation model」未实现。
