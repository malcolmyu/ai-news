为什么需要多智能体系统？

265|
266| 一个 Agent 的上下文窗口有限、一次只能聚焦一个任务、出错时没有监控和回收机制。多智能体架构的本质是 分工 + 约束 + 反馈：把大问题拆成小任务，每个子 Agent 只有少量工具，用代码而不是 Prompt 做验收。结果是更可靠、可追踪、可迭代的工作流。 267|

02 · Architecture Patterns
322|

四大架构编排模式

323|
324|
325|

🧠 中央协调 (Orchestrator)

326|
主 Agent 不写代码，只分解任务、分配子 Agent、聚合结果。Hermes 的多 Agent 编队、OpenAI Codex CLI 的 Plan → Code → Review 均属此模式。子 Agent 返回文件路径和状态码。
327|
328|
329|

📡 事件驱动 (Event-Driven)

330|
Agent 通过消息队列通信。一个 Agent 的输出触发下一个 Agent 的输入。适合流式处理 pipeline（如 RSS 采集 → 摘要 → 发布）。LangChain 的 graph 运行时是其代表。
331|
332|
333|

🔄 循环迭代 (While Loop)

334|
Rust/Python while 循环启动新 CLI 会话，文件系统传递上下文。代表：Ralph。局限：自己开发自己测试时效果一般，缺少独立视角。
335|
336|
337|

🏛️ 专家编队 (Swarm)

338|
每个 Agent 是领域专家，路由层根据任务类型派发。Stripe 的每个 Agent 只看筛选子集工具。Vercel 将工具从 15 个减到 2 个，准确率从 80% → 100%。

04 · Implementation
440|

多 Agent 编队的实现关键

441|
442|
443|

🧩 主 Agent 不写代码

444|
协调层只负责：分解任务 → 分发 → 聚合结果。不参与开发、不碰文件。始终从状态码和摘要理解进度，按里程碑输出确认。
445|
446|
447|

📁 文件系统即通信

448|
子 Agent 输出到文件，主 Agent 读取文件。不需要 RPC、消息队列。文件路径 + 状态码 = 足够的生产级通信协议。
449|
450|
451|

✂️ 工具越少越好

452|
每个子 Agent 只看筛选子集工具。Vercel 实验：15→2 个工具，准确率从 80% 跳到 100%。约束比指令有效。
453|
454|
455|

🔄 错误剥离原则

456|
写 Bug 的 Agent 修 Bug，提 Bug 的 Agent 验收。不交叉、不混淆。修正循环最多 3 次，超出则留人工介入。

Hermes Agent

468|
469| 基于 delegate_task 的原生多 Agent 支持。支持并行子 Agent（最多 3 并发）、隔离上下文、Acp 协议集成。

470| 亮点：单个会话内自动拆解、多 Agent 并行、结果聚合。 471|
472|
473|
474|

Ralph

475|
476| Rust while 循环驱动 Claude CLI，文件系统传递上下文。轻量但缺乏隔离。

477| 亮点：完全无服务器依赖，纯 CLI 生态。 478|

OpenAI Codex CLI

482|
483| Plan → Code → Review 三段式。每个阶段一个 Agent 做一件事。但 review 阶段不是独立第三方。

484| 亮点：官方维护，与 GPT 生态深度整合。 485|
