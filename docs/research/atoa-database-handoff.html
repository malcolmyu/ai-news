AtoA 实践：多 Agent 协作为什么用数据库做交接层

一位大厂法务在做「邮件 → 合同审核」AI 工作流时的真实踩坑与选型：单 Agent 长链条跑不通，直接 AtoA（Agent @ Agent）指令不受控，本地文件夹中转有四道硬伤——最终落到「两个 Agent + 数据库持久化交接层」的生产者-消费者模式。核心洞见一句话：交接层要传「数据」，不要传「指令」。

01 · 核心命题

交接层要传「数据」，不要传「指令」

多 Agent 协作的关键不在「怎么把两个 Agent 连起来」，而在中间交接什么。作者试了三种方式后给出的结论：让上游把结构化信息写进数据库、下游轮询读取，而不是让 Agent 之间直接传自然语言指令。因为自然语言 prompt 天然携带不确定性、信息冗余、指令覆盖，而数据库字段是刚性契约——字段、类型、有无值都可校验，下游拿到的是数据而非指令。
"数据库交接的契约是刚性的……下游的 Agent 拿到的是数据，而不是一个指令，它就会直接按照你之前训练好的既定流程去走。"— 大厂法务实践分享
02 · 场景背景

一条「邮件 → 合同审核」的定时工作流

作者的工作流很典型：定时从邮箱取邮件 → 筛选 → 下载附件 → 解析附件 → 执行合同审核 → 输出结论。他原本已经有一个成熟的审核 Agent，想再补上邮件处理能力。
最初的直觉是把邮件处理直接塞进同一个 Agent 的 prompt，让一个 Agent 跑完整条链路。试下来才发现，链条一长，四类问题接踵而至。
03 · 反模式

单 Agent 长链条的四个问题

把取邮箱、筛邮件、下附件、解析、审核、输出结论全塞进一个 Agent，链路是串行的，每一步都依赖上一步。一旦链条变长，问题集中爆发：
问题 具体表现
时间长 串行链路，每步 10 秒也要六七十秒；邮件一多，单次处理时间失控
稳定性差 中间任何一步出错都会卡死整条链，只能从头再来
排查困难 Agent 内部卡住，很难定位到底是哪一步出了问题
状态不可见 中间态不落盘，失败了只能从头重跑

唯一的例外：Harness 类可观测工具

作者特别点出：除非你用的是 Harness 这类能看清 Agent 内部每一步执行情况（代码执行、工具调用、完成状态）的平台，否则普通人用的「平台包装好的 Agent」看不到后端，中间状态不可见就成了硬伤。这跟「可验证性优先」的 Harness 工程一脉相承——交接层的价值本质是让状态可观测、可校验。
04 · 方案选型

三种交接方式，逐一对决

决定拆成两个 Agent 后，问题变成「怎么连」。作者逐一试了三种方式，最终只留数据库这一种。
方式 结论 核心问题
直接 AtoA（@ 下游） 放弃 交接自然语言 prompt，不确定、冗余、覆盖、难校验
本地文件夹 放弃 无状态、无并发控制、无元数据、不可追溯
数据库持久化交接层 ✅ 最终方案 契约刚性、可校验、可追溯，还兼做法务工作台底座
05 · 直接 AtoA 的坑

上游指令会「自作聪明」，因为交接的是自然语言

作者试过让 Agent 直接 @ 下游 Agent。正常期待是「上游做完告诉下游 OK 你可以下一步了」，但实际上游每次都会顺带多写一点指令——比如突然补一句「顺便检查一下附件格式」，下游就可能被带偏去干别的。从技术角度拆解，问题的本质是：AtoA 直接调用交接的是自然语言 prompt，而自然语言有四个固有特性：

自然语言 prompt 的四个特性

  • 不确定性：同一意图，每次生成的指令都可能不完全一样
  • 信息冗余：根据上次处理情况「自作聪明」地多给补充指令
  • 指令覆盖：覆盖下游已经训练好的 skill/脚本，逼它另寻新路，反而弃用了最优化方案
  • 难以校验：无法像校验数据库字段那样校验上游每次输出的 prompt
要让 AtoA 直接调用变得可控，需要把上游输出变成结构化、契约性的输出——但那往往需要在平台层做 schema 校验，对应用层的普通人来说不简单、也不划算。所以作者在两个约束下放弃了这条路线：一是当前内部应用平台不提供结构化输出控制方案；二是他的场景不需要秒级响应，数据库轮询完全够用，等平台有了结构化通信协议再升级不迟。
06 · 本地文件夹的四道硬伤

文件夹做交接层，是个「盲盒」

本地读写肯定最快，但作者发现让上游把附件下载到本地、下游去本地拿，中间流程很容易断——多业务线分目录后，下游经常「找不着」文件，还得人工去找。回头从技术角度审视，本地文件夹作为交接层有四道硬伤：
硬伤 后果
没有状态 文件有没有全部下完、有没有全部处理完，都没有记录，就是个盲盒
没有并发控制 上游一直写、下游一直读，同一目录同时读写可能冲突
没有元数据 只存附件，正文里的背景信息、关注重点全在审核时丢失了
不可追溯 处理失败后很难快速知道当时处理的是哪一封邮件，附件和邮件对不上号
数据库恰好逐一补齐：文件和邮件所有信息能对应得上；发件人、抄送人、主题、正文都能作为元数据落库，审核时不会丢信息。
07 · 最终方案

生产者-消费者 + 错峰轮询

回头看，作者发现这个方案其实符合技术上的常规思路——生产者和消费者模式：上游 Agent 是生产者，下游 Agent 是消费者，中间用一个队列/存储来解耦。

邮件 Agent（生产者）

每个整点跑一次：检索邮箱 → 下载附件 → 抽取元信息 → 写入数据库（附件、发件人/抄送人、主题、正文等全部源信息）。

审核 Agent（消费者）

每个半点跑一次：从数据库轮询抓取信息 → 解析附件 → 执行审核 → 输出结论。
拆成两个 Agent、数据库解耦后，前面四个问题全部解决：每个环节可以单独观测、单独重试、单独替换。比如今天用 Outlook 邮箱、明天想换 163 邮箱，接口变了，只要改邮件处理这一个 Agent，互不影响。
"上游 Agent 是生产者，下游 Agent 是上游生产的数据的消费者，中间再有一个队列或存储来解耦。"— 大厂法务实践分享
08 · 判断标准

什么时候直接 AtoA，什么时候数据库中转

作者给出一条简单可套用的判据：
条件 推荐方案
交接内容简单、链路短、需要强实时性 直接 AtoA
链路长、环节多、不要求秒级响应 数据库中转（更稳定）
作者当前场景「整点轮询 + 半点轮询」的错峰处理完全够用，所以他选择先等平台侧有了结构化通信协议，再升级到真正的 AtoA。
09 · 额外价值

数据库不只是中转层，更是法务工作台的数据底座

作者特别强调了一个前瞻视角：未来想做法务工作台（看统计数据、一键回复邮件），数据库就能直接成为数据底座。所以第一次抓取时就把所有源信息（含正文）都存进去，避免以后再抓一遍——那既耗时又耗 token。
