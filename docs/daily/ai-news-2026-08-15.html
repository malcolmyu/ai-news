Boris Cherny @bcherny
A weird experiment I've been trying the last few weeks is having Claude take over day-to-day maintenance of our apps. Seeing early signs of life that this might be possible. The setup is straightforward: we have a Slack channel called proj-claude-maintains-apps. In it, Claude Tag runs a bunch of daily routines across iOS, Android, Desktop, web, CLI, and Agent SDK: - Crash fuzzer: open the app in a simulator and tap around to find ways to crash it, then root cause and fix the crashes - Dup unifier: scans the codebase for similar-yet-slightly-divergent abstractions, and puts up PRs to unify them - Dead-code remover: removes statically unreachable code, and adds logging to suspected dead code to check if it's really dead and if so, remove it the next day - Abstraction police: fixes leaky abstractions - a bunch more.. Results have been surprisingly positive. Over the last few weeks, these routines have opened 388 PRs across our repos, 180 of which we merged after Claude Code Review + human review. We're now thinking about how to streamline this to make merging these kinds of mechanical changes easier. Claude generally gets these PRs right on the first shot, and if it doesn't, we ask Claude to tune its routines so it's better the next day. Sometimes it takes a few days of tuning. To try a similar workflow, ask Claude Code or Tag, or create some routines directly at https://t.co/Z70hStEBH6. A few of the actual prompts I used below. Has anyone experimented with similar workflows?
这几周我在试一个怪实验：让 Claude 接管我们应用的日常维护，已经看到一点「这事可能真能成」的早期迹象。做法很简单，我们开了个叫 proj-claude-maintains-apps 的 Slack 频道，Claude Tag 在里面每天跑例行任务，覆盖 iOS、Android、桌面、Web、CLI 和 Agent SDK：崩溃模糊测试（在模拟器里乱点找崩溃、定位并修复）、重复抽象统一器、死代码清理、抽象警察等等。结果意外地好：这几周开了 388 个 PR，其中 180 个经 Claude Code Review + 人工审查后合并。Claude 通常一次就写对，写不对就让它调例行任务，第二天做得更好。想试的话去问 Claude Code 或 Tag。

Nikunj Kothari @nikunj
Grok Bot is a fantastic release.. the UX, the design, the onboarding :chefs-kiss: But I go back and forth on this a lot: Will users (personal and business) want one super agent that holds all the context or sub agents that are designated to do a slice of tasks? If we treat agents as humans, then the Grok Bot design makes a ton of sense. It allows us to compartmentalize tools, context, outcomes for that person’s division. You reach out to that bot for that specific goal that you have in mind. But, if you treat agents as Jarvis, you want a master agent that just gets the job done. It might create and coordinate all the bots (and dare I say the communication/context) that might be needed to do the task. But the interface is 1:1 vs. 1:many. My guess is it’ll veer towards the one master agent over time who can then act as an orchestrator who reads / understands the bots you create. But starts narrow as most of the companies are doing it now. PS: I understand the core engineering constraints (context windows, tool use, simplicity, cost etc) why companies are choosing task/singular outcomes today. Primarily thinking this from a design / product side.
Grok Bot 是个很棒的发布，UX、设计、onboarding 都挑不出毛病。但我一直纠结一件事：用户到底想要一个掌握所有上下文的超级 agent，还是一堆各管一摊的子 agent？如果把 agent 当人看，Grok Bot 的设计很合理——按人的分工隔离工具、上下文和结果。但如果把 agent 当 Jarvis，你想要一个能把活干完的主 agent，它自己创建并协调所需的 bot。我的猜测是：长期会走向一个主 agent 当编排者，读懂并理解你创建的 bot；但一开始还是像大多数公司现在这样，从窄场景做起。
