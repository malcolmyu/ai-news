今日头条
Daytona CEO Ivan Burazin：AWS 和 Azure 的架构跑不了自主 Agent——The MAD Podcast 最新访谈中，Ivan 给出了一个深刻论断：超大规模云的架构是为无状态应用设计的，就像卡车和跑车都有四个轮子但底盘完全不同。Agent 需要的是状态机——CPU、内存、硬盘绑在同一台物理机上的专属电脑，能像人一样持续工作。他预测全球 CPU 短缺即将来临，因为每个 Agent 都需要自己的计算机，而 RL 训练又吞噬大量 CPU 资源。同时他对 Transformer 架构保持清醒怀疑："我不觉得现在的模型架构是终局。"
Agent 工程实践大爆发：依赖瘦身、Eval 方法论、Token 效率——OpenClaw 创始人 Steipete 将图片处理依赖从 140MB 瘦身到 2MB，用 Rust 编译到 WebAssembly 的 photon 替代 Sharp+Jimp。Garry Tan 提出三个模型交叉评分的 Eval 方法论，迭代到 10 分制。Peter Yang 引用 Ryan Carson 经验：Agent 时代应该"先建能造 MVP 的系统"。工程纪律正在成为 AI Agent 时代的真正护城河。
Agent 工程

OpenClaw 创始人 Peter Steinberger：把 140MB 依赖砍到 2MB

Peter Steinberger 密集分享了三项 Agent 工程实践：① 做减法——用 Rust 编译到 WebAssembly 的 photon 替代了 Sharp 和 Jimp，依赖从 140MB 降到 2MB，证明了 Agent 运行时需要全新的工程范式；② Token 效率——写 skill 时要注意 token 效率，太多 skill 文件写得跟书一样厚全塞进每一轮 context，不必太在意语法，实用优先；③ 调侃安全圈 "There's security, and there's clankers"，在 Agent 时代重新思考安全的边界。

AI 与经济

Box CEO Aaron Levie：AI 不会消灭工作，但会淘汰跟不上的人

Aaron Levie 引用高盛 CEO 的观点反击 AI 导致失业的悲观论——核心论证：如果几十年前你看到现在的工作效率，你会以为工作早没了。但实际发生的是，有人用自动化做出更好的产品，所有人的期望被拉高，跟不上的人被淘汰。不是工作变少，而是工作变深：分析师产出更多财务分析、律师提供更全面的法律意见、医疗提供更深入的诊断。这个视角将 AI 从"威胁"重新定义为"升级"，关键在于你能否跟上期望曲线的斜率。

播客深度

The MAD Podcast：为何 AWS 和 Azure 跑不了自主 Agent

Daytona CEO Ivan Burazin 在 The MAD Podcast 中系统阐述了他对 Agent 基础设施的判断。核心论点：每个 Agent 至少需要一个沙盒——不是"隔离环境"那么简单，而是 Agent 的专属电脑，带 CPU、内存、硬盘、浏览器、文件系统。Agent 本质上是数字知识工作者，而知识工作者需要工具才能产出。
超大规模云的"错误底盘"
AWS/Azure 的架构是为无状态应用设计的，不是为 Agent 设计的。就像卡车和跑车都有四个轮子和发动机，但底盘完全不同。传统云假设你的 app 不会在运行时被改变；Agent 恰好相反，它需要在运行时不断安装工具、写代码、开浏览器。
Agent 需要的是状态机，不是无状态函数
Daytona 把 CPU、内存、硬盘全绑在同一台物理机上（而非网络盘），IOPS 从数十万跳到数千万。这让 Agent 可以像人一样持续工作——打开笔记本干活、合上盖子、换个设备继续。这是从"云原生"到"Agent 原生"的范式转换。
全球 CPU 短缺正在来临
GPU 短缺广为人知，但 Ivan 指出 SemiAnalysis 预测今年 10 月 CPU 也会不够用。原因？每个 Agent 都需要自己的计算机，而 RL 训练又吞噬大量 CPU 资源。基础设施的瓶颈正在从"能不能训练"转向"能不能运行"。
对模型架构的清醒判断
Ivan 不认为 Transformer 是终点："有人用湿件复刻了果蝇大脑，能像果蝇一样行动。如果复刻一个通用人类大脑呢？我不觉得现在的模型架构是终局。"这种从底层硬件到顶层架构的系统性思考，在 AI 基础设施创业者中并不多见。

今日思考
Agent 基础设施的范式转换：云原生 → Agent 原生
Ivan Burazin 的诊断切中了一个被大多数人忽视的问题：AWS/Azure 的设计哲学是为无状态应用服务的，而 Agent 是状态机。Steipete 的 140MB→2MB 依赖瘦身实验在微观层面证明了同样的命题——Agent 运行时需要全新的工程范式。当每个人都在讨论模型能力时，少数人在重新设计 Agent 的"底盘"：从存储架构（本地盘 vs 网络盘）到依赖管理（2MB vs 140MB），再到执行模式（24 小时持续运行 vs 请求-响应）。Agent 基础设施的竞争，不是谁家 GPU 更多，而是谁的"底盘"更适合 Agent 的工作方式。
工程纪律正在成为 Agent 时代的护城河
Garry Tan 的 Eval 方法论（三个模型交叉评分 → 迭代到 10 分）和 Peter Yang 引用的 Ryan Carson 经验（先建系统再建 MVP）指向同一个方向：Agent 时代的生产力瓶颈不在模型能力，而在工程纪律。代码写得好不好另说，文档和 Eval 写得好不好才是真正的护城河。Nikunj Kothari 说 VC 必须持续 build 才能保持在前沿，Aaron Levie 说 CEO 必须亲自用 AI 才能避开"AI 精神病"——共同点是什么？亲力亲为。在 AI 工具极大降低执行门槛的今天，最大的竞争优势不是拥有最好的模型，而是拥有最紧的 build-eval-iterate 循环。
"Prompter"：从个人技能到组织职能
Garry Tan 转发的"prompter 将成为新工种"推文不只是一个有趣的概念——它标志着一个严肃的产业趋势。当公司开始为 prompt engineering 设立专职岗位时，意味着 AI 已经从"辅助工具"升级为"组织基础设施"。正如 DevOps 在 2010 年代从个人技能演变为专属工程学科，prompt engineering 正在经历同样的制度化过程。唯一的区别是速度：这次快得多。
AI 时代的身份危机：真实 vs 伪造
Amanda Askell 被人冒充写博客的事件不是孤例——它是 AI 生成内容泛滥的必然结果。当任何人都可以用 Claude 生成一篇"某知名人物风格"的内容并署名时，身份验证和内容溯源将成为 AI 时代的核心基础设施需求。Dan Shipper 引用的教皇 AI 声明从另一个角度切入同一问题：在这个真假边界模糊的时代，人类需要重新思考技术是用来连接还是隔离彼此。这是一个技术问题，更是一个哲学问题。
今日一问：Ivan Burazin 说 Agent 需要的是状态机而非无状态函数，Steipete 把依赖从 140MB 砍到 2MB，Garry Tan 和 Peter Yang 都强调工程纪律。如果你的团队正在构建 AI Agent 应用，你们的"底盘"设计——从基础设施选择到 Eval 方法论——是基于"无状态应用"的老范式，还是基于"状态机"的新范式？
